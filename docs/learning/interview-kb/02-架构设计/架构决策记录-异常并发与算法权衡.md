## 决策 1：ExceptionGuardAdvisor order 调整 + ChatServiceImpl 双重兜底去留

### 背景

当前异常处理存在**两层兜底**：

| 层 | 位置 | 方式 |
|----|------|------|
| 外层 | `ChatServiceImpl` 3 个流式方法 | `.onErrorResume(e -> ...)` 区分 BusinessException / 未知异常 |
| 内层 | `ExceptionGuardAdvisor` (order=`MAX_VALUE`) | `adviseStream()` 内 `.onErrorResume(BusinessException.class, ...)` |

### 为什么会有两层？

**历史遗留**。Spring AI M6 时期，`DefaultAroundAdvisorChain` 的 Micrometer Observation scope 会阻断流式路径的 `.onErrorResume()` 信号，导致 ExceptionGuard 的兜底不生效，异常直接穿透到 ChatServiceImpl。因此在 ChatServiceImpl 加了一层外层兜底作为临时修复。

### Advisor 执行顺序

```
order 越小 → 越外层（先执行，包裹后面的 Advisor）

当前（MAX_VALUE = 最内层）：
  ContentGuard(0) → MCMA → RagInjection(15) → PromptOptimize(20)
    → Logging(30) → ExceptionGuard(MAX)
                        ↑ 只包裹模型调用，其他 Advisor 的异常抓不到

改为 MIN_VALUE 后（最外层）：
  ExceptionGuard(MIN) → ContentGuard(0) → MCMA → RagInjection(15)
    → PromptOptimize(20) → Logging(30) → 模型调用
       ↑ 包裹整条链，任何一层抛异常都能兜底
```

### 方案对比

| | 方案 A：删外层 | 方案 B：保留双重 |
|---|---|---|
| **做法** | ExceptionGuard 改 MIN_VALUE，删 ChatServiceImpl 的 3 处 `.onErrorResume` | ExceptionGuard 改 MIN_VALUE，外层不动 |
| **异常路径** | 唯一路径：ExceptionGuard → 友好消息 | ExceptionGuard 兜 99%，外层兜最后的 1% |
| **代码维护** | 异常处理只在一处，改一处生效 | 两处逻辑需同步维护 |
| **风险** | ExceptionGuard 有 Bug 则直接炸客户端 | 外层是死代码（ExceptionGuard 正常时永远不触发），造成阅读困惑 |
| **推荐** | ✅ 如果 Micrometer 的坑已修复，更干净 | ❌ 死代码即技术债 |

### 面试要点

- **为什么不在 Controller 层统一 try-catch？** → 流式场景 Controller 拿到的是 `Flux<T>`，不是同步结果。Reactor 的错误信号在 subscribe 时才传播，Controller `try-catch` 抓不到。必须在 `Flux` 流内部 `.onErrorResume()`。
- **为什么 ExceptionGuard 是 Advisor 而不是 Filter/Interceptor？** → Advisor 是 Spring AI 的拦截器机制，能访问 Prompt 上下文和 ChatMemory，异常时能返回 `AssistantMessage`（符合 AI 对话协议），而 Filter 只能返回 HTTP 错误码。
- **order=MIN_VALUE 与 order=MAX_VALUE 的本质区别** → 不是"先执行/后执行"的问题，而是 **try-catch 的嵌套层级**。MIN_VALUE 是最外层 try-catch，MAX_VALUE 是最内层 try-catch（只包模型调用）。

## 决策 2：Rerank 多维度分数的量纲归一化

### 背景

`RagRerankerImpl` 当前的三路加权公式（`RagRerankerImpl.java:31-33`）：

```java
finalScore = vectorScore × 50.0    // 余弦相似度 [0~1]
           + keywordScore × 15.0   // 标签命中计数 [0~N]
           + metadataScore × 10.0  // 元数据匹配分 [0~M]
```

三路分数的**原始量纲完全不同**——vectorScore 是 0~1 的浮点，keywordScore 和 metadataScore 是无上限的整数。即使有权重，一个 metadataScore=10（×10=100）就能直接碾压 vectorScore=1.0（×50=50）的完美语义匹配，**权重形同虚设**。

### 具体例子

```
图A: vector=0.6, kw=5, meta=20  → 0.6×50 + 5×15 + 20×10 = 30 + 75 + 200 = 305
图B: vector=0.9, kw=1, meta=2   → 0.9×50 + 1×15 + 2×10  = 45 + 15 + 20  = 80
```

图B 语义上更匹配（0.9 vs 0.6），但因为关键词和元数据分数差异被图A 远远甩开——**排名由量纲大的维度主导**。

### 方案对比

| | 方案 A：批次内 min-max 归一化 | 方案 B：硬上限截断 |
|---|---|---|
| **做法** | 每批候选集内部对每个维度做 `(x-min)/(max-min)` 到 [0,1]，再加权 | 给 keywordScore 设上限 30、metadataScore 设上限 45，重新配权重 |
| **优点** | 自适应，权重即真实影响力比例 | 简单稳定，分数跨批次可比，调试直观 |
| **缺点** | 同一图在不同批次分数不可比（调试困惑） | 上限值需手动校准（keyword 30 够不够？metadata 45 偏保守？） |
| **适用场景** | 不关心分数绝对值，只关心批次内相对排序 | 需要分数有绝对意义（如"0.6 以上=好结果"阈值判断） |

### 面试要点

- **为什么不直接用 vectorScore 排序？** → 语义匹配有盲区。比如用户搜"赛博朋克风格"，embedding 可能召回色调相近但不是赛博朋克的图。关键词标签命中、元数据（分类/格式）命中可以修正纯语义排序的偏差。本质是**多信号融合提升检索精度**。
- **min-max 归一化的数学风险** → 当批次内所有候选的某个维度值相同时（max=min），分母为 0。通常兜底为 0.5 或直接跳过该维度。
- **业界做法参考** → 推荐系统的多目标融合中，更多用方案 A（归一化后线性加权），因为权重有可解释的业务含义。方案 B 常用于对延迟敏感、无法承受批次级计算的场景。

## 决策 3：Repository save() 的并发安全 —— INSERT ON CONFLICT vs @Transactional

### 背景

两个 Repository 的 `save()` 都用了"先查后写"模式，存在竞态窗口：

**`PostgresPictureAiProfileRepository.save()`**（第 49-65 行）：
```java
if (findByPictureId(profile.pictureId()).isPresent()) {
    return update(profile);  // 存在 → 更新
}
// 不存在 → INSERT（第 53-64 行）
```
`picture_id` 是业务键（外键指向 gallery_picture），有唯一约束。

**`PostgresGalleryPictureRepository.save()`**（第 72-98 行）：
```java
if (picture.id() != null) {
    return update(picture);  // id 非空 → 更新
}
// id=null → INSERT（第 76-97 行）
```
`id` 是自增主键，无业务唯一键。

### 为什么 PictureAiProfile 适合 INSERT ON CONFLICT

竞态场景：两个线程同时 `findByPictureId(10)` → 都返回空 → 都执行 INSERT → 第二个炸 duplicate key。

修复：一行 SQL 搞定，原子操作无需事务：
```sql
INSERT INTO picture_ai_profile (...) VALUES (...)
ON CONFLICT (picture_id) DO UPDATE SET ...
-- 变为幂等 upsert，无论多少并发都不会炸
```

### 为什么 GalleryPicture 不适合 INSERT ON CONFLICT

- `id` 是自增主键，新记录 id=null，PG 中 `NULL != NULL`，`ON CONFLICT (id)` 永远不触发。
- `pic_hash` 列没有唯一约束（去重靠 Service 层的 `findByHash()` 查重）。
- 竞态发生在 Service 层：`findByHash() → 返回空 → save()`，两步之间有窗口。

### 方案对比

| | 方案 A：各用各的 | 方案 B：统一加锁 |
|---|---|---|
| **PictureAiProfile** | `INSERT ON CONFLICT`（SQL 原子） | Service + `@Transactional` + 悲观锁 |
| **GalleryPicture** | Service + `@Transactional`（事务包裹查重+插入） | 同左 + 乐观锁/分布式锁 |
| **复杂度** | 低，因表制宜 | 高，分布式锁是重型武器 |
| **适用场景** | 单机部署，DB 事务足够 | 多实例部署需跨进程排他 |
| **推荐** | ✅ 务实选择 | 过度设计 |

### 面试要点

- **什么场景用 ON CONFLICT 什么场景用 @Transactional？** → 有唯一业务键（非自增主键）→ ON CONFLICT，一行 SQL 原子；无业务唯一键，竞态跨多行或多表 → Service 层事务。
- **@Transactional 能保证绝对不重复吗？** → 默认隔离级别 READ_COMMITTED 下，两个并发事务都能读到"无重复"然后各自 INSERT。要绝对安全需要 `SERIALIZABLE` 隔离级别或在 `pic_hash` 上加唯一约束 + ON CONFLICT。
- **当前代码的哈希去重也有竞态** → `GalleryService` 的 `findByHash()` + `save()` 不是原子的。高并发上传同一张图会产生重复记录。

## 决策 4：图片 AI 画像分析 —— 同步 vs 异步

### 背景

`image_generation` 模式下，同一张用户上传的图片**被调了两次视觉模型**（`glm-4.5v`）：

| 次数 | 触发路径 | 用途 | 时机 |
|------|---------|------|------|
| 第 1 次 | `autoSaveToCacheGallery()` → `@Async` 事件 → `PictureAutoAnalysisListener` | 分析图片特征，存到 `picture_ai_profile` 表 | 异步（不阻塞请求） |
| 第 2 次 | `prepareRagContext()` 同步调用 | 提取视觉特征文字，作为 RAG 向量检索 query | 同步（阻塞请求） |

**同一张图、同一个模型，调了两次**，仅 prompt 不同。浪费一次 API 调用的钱和时间。

附带问题：第一次是异步的，画像结果对当前请求不可见（分析还没跑完请求就返回了）。如果后续有更多模块需要视觉分析结果（内容审核、自动标签等），每个模块都要独立调一次 LLM。

### 方案对比

| | 方案 A：改为同步 | 方案 B：保持异步 + 缓存 |
|---|---|---|
| **做法** | 入库后立即调视觉模型，结果同时用于 RAG 检索和画像存储 | prepareRagContext() 结果写入缓存，异步监听器优先读缓存，命中则跳过 |
| **模型调用次数** | 1 次 / 图 | 1 次 / 图（缓存命中时） |
| **上传延迟** | +2~5 秒（视觉模型调用） | 不增加（后台异步跑） |
| **画像当前请求可见** | ✅ 立即可见 | ❌ 异步，对当前请求不可见 |
| **系统复杂度** | 低，逻辑线性 | 高，引入缓存层（过期/失效/一致性） |
| **推荐** | ✅ 用延迟换简单 | 用复杂度换低延迟 |

### 为什么方案 A 更合理

1. **上传不是高频操作**，2~5 秒在生图场景中完全可接受（生图本身要等更久）。
2. **画像结果即时可用**——后续如果有内容审核、自动标签等模块，可以直接复用，不需要各自调 LLM。
3. **逻辑简单**——入库 → 分析 → 存储 + 检索，一条同步链路，没有缓存一致性问题。

### 面试要点

- **什么时候异步比同步好？** → ① 操作不阻塞主链路（如发通知、写日志）；② 结果不需要当前请求立即使用；③ 失败可以接受（不需要强一致性）。当前场景的画像分析**后续链路依赖其结果**（RAG 检索），同步更合理。
- **@Async 的坑** → Spring 默认用 `SimpleAsyncTaskExecutor`（每次新建线程，无复用）。生产环境需要配置线程池（corePoolSize/maxPoolSize/queueCapacity），否则高并发下线程爆炸。此外 `@Async` 方法必须 public + 非本类调用（Spring AOP 代理限制）。
- **如果视觉模型调用要 10 秒怎么办？** → 前端可以先返回"图片已上传，正在分析中"，用 SSE 推送分析进度。本质是"同步处理 + 异步通知"，不是"异步处理"。
