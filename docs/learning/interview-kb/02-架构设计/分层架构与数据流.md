```
com.zzp.aiagent
├── controller/     REST 入口层 —— 只做 HTTP 适配
├── service/        业务逻辑层（接口） —— 业务编排
│   ├── ReferenceRetriever.java      ← 新增: RAG 检索抽象接口
│   ├── ChatMediaService.java        ← 新增: Media 构造服务

│   │   ├── ChatMediaServiceImpl         ← 新增: Media 构造 + MIME 解析
│   │   └── ConversationLimitServiceImpl ← 新增: 会话上限判断
├── repository/     数据访问层（接口） —— 持久化
│   └── impl/       JDBC 实现
├── manager/        基础设施管理器 —— 存储/缓存/向量
├── api/            外部 API 调用层 —— 智谱 HTTP 客户端
├── domain/         领域模型 —— 按聚合根分包子包

└── utils/          工具类（PromptTemplate）
```

## 调用规则

```
Controller ──→ Service(接口) ──→ Repository(接口) ──→ JDBC
                  │                    │
                  ├──→ Manager         ├──→ Manager
                  ├──→ API             └──→ Event
                  └──→ Event
```

- **Controller**：只做 HTTP 适配 + @Valid 校验 + BaseResponse 包装。用 @RequiredArgsConstructor 注入 Service 接口
- **Service**：业务编排 + @Transactional。不碰 HTTP 细节（HttpServletRequest/Response 不在 Service 层出现）
- **Repository**：数据访问接口 + 实现分离。实现直接用 NamedParameterJdbcTemplate（非 JPA/MyBatis）
- **Manager**：基础设施（ObjectStorageService/VectorIndexService/RedisChatMemory），可被 Service 和 Repository 调用
- **API**：外部服务客户端（智谱），实现 Service 接口（如 CogViewImageApi implements ImageDownloadService）


## 核心设计决策

### 1. Repository 用 NamedParameterJdbcTemplate 而非 JPA

- 原因：GalleryPicture 是 24 字段 record，字段映射复杂，手写 SQL 更可控
- 代价：需要手写 RowMapper 和 Insert/Update SQL
- pgvector 的向量操作 Spring AI 已封装（VectorStore 接口），不需要手写

### 2. Manager 层的定位

Manager 是"基础设施管理器"，不同于 Service（业务逻辑）和 Repository（数据访问）：
- `ObjectStorageService`：文件系统抽象，不涉及业务规则
- `PgVectorIndexService`：封装 pgvector 的 CRUD，提供业务无关的向量索引能力
- `RedisChatMemory`：实现 Spring AI 的 ChatMemory 接口，管理 Redis List 的读写

### 3. 事务边界在 Service 层

`@Transactional` 加在 Service 方法上（如 `GalleryServiceImpl.upload()`），Repository 不管理事务。事件发布（`ApplicationEventPublisher.publishEvent()`）在事务提交后触发监听器（`@TransactionalEventListener` 或独立 `@Async`）。

### 4. 事件驱动的异步解耦

图片上传后异步触发 AI 画像分析（`PictureAutoAnalysisListener` + `@Async`），不阻塞上传接口的响应。

### 5. ChatServiceImpl 拆分 (Phase 3)

ChatServiceImpl 从 575 行的上帝类薄化为编排层：

| 职责 | 拆分到 |
|------|--------|
| Media 构造 + MIME 解析 + Base64 剥离 | ChatMediaService |
| 会话消息上限判断（Redis 优先 → PG 回退） | ConversationLimitService |
| 模式路由 + RAG 装配 + Advisor 调用 | ChatServiceImpl（保留，薄编排） |

注入关系：ChatServiceImpl → ChatMediaService + ConversationLimitService
