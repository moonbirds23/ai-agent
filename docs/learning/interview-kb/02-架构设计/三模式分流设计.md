# 三模式分流设计

## 三种对话模式

ChatRequest 通过 `mode` 字段指定对话模式，在 ChatServiceImpl.chat() 入口处以 Java 21 switch expression 分叉。

| 模式 | mode 值 | 调用链 | AI 调用次数 | 是否走 Advisor 链 |
|------|---------|--------|------------|-------------------|
| 文本讨论 | `chat` | ChatClient(.call) | LLM ×1 | ✅ |
| 图片分析 | `image_analysis` | VisionAnalysisService | Vision ×1 | ❌ 直接调视觉 API |
| 图片生成 | `image_generation` | ChatClient(.call) + ImageGenerationService | LLM ×1 + Vision(可选) + CogView ×1 | ✅ + RagInjection |

## 模式解析逻辑

```java
private String resolveMode(ChatRequest request) {
    String mode = request.mode();
    if (mode != null && !mode.isBlank()) {
        return mode.trim().toLowerCase(Locale.ROOT);   // 显式 mode 优先
    }
    return Boolean.TRUE.equals(request.generationMode())
            ? ChatRequest.MODE_IMAGE_GENERATION         // 兼容旧版 generationMode
            : ChatRequest.MODE_CHAT;                    // 默认讨论模式
}
```

优先级：**显式 mode > generationMode(兼容) > chat(默认)**

## 三条路径的关键差异

| 维度 | chat | image_analysis | image_generation |
|------|------|---------------|-----------------|
| 图片自动入库 | ✅ (有图时) | ✅ (有图时) | ✅ (有图时) |
| RAG 装配 | ❌ | ❌ | ✅ prepareRagContext() |
| MCMA 记忆窗口 | 10 条 | N/A | 50 条 |
| RagInjection | ❌ | ❌ | ✅ |
| ChatMemory 写入 | MCMA 自动 | 手动 add() | MCMA 自动 |
| 响应 type | `"chat"` | `"image_analyzed"` | `"image_generated"` |
| 调试数据 | null | null | RAG 三层 trace 数据 |

**Phase 1 修复**：流式生成模式之前缺少 `RagInjectionAdvisor.KEY_RAG_AUGMENTED` 参数，导致 RAG 增强完全失效。已补充参数并统一使用 `RagInjectionAdvisor.applyAugmentation()` 封装。

## 为什么 image_analysis 绕开 Advisor 链

分析模式不需要 LLM 文本生成，只需要纯视觉模型返回结构化分析结果。走 Advisor 链：
1. 浪费（ContentGuard 重复校验、PromptOptimize 无意义优化）
2. ChatClient 的输出格式是 ImageAgentResponse，与 VisionAnalysisResult 不兼容
3. 分析结果不做 RAG 增强

所以直接调 `visionAnalysisService.analyze()`，然后手动写入 ChatMemory。

## 为什么生成模式 MCMA 窗口是 50 条（讨论模式是 10 条）

- 讨论模式：10 条足够维护简单对话上下文
- 生成模式：需要更多历史上下文来理解用户的**风格偏好演化**，帮助 LLM 输出更精准的 imagePrompt

## 流式与非流式双接口

两个接口共享同一套业务逻辑（模式分叉 + RAG 装配 + Advisor 链），区别只在：
- **非流式**：`.call().entity(outputConverter)` → 一次性返回结构化 JSON
- **流式**：`.stream().content()` → SSE 逐 token 推送，末尾客户端拼装解析

流式路径需要额外处理：`onErrorResume` 两层（BusinessException + Exception）确保流不中断。
