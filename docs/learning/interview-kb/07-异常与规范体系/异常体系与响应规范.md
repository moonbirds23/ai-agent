# 异常体系与响应规范

## ErrorCode —— int 码枚举

```java
public enum ErrorCode {
    SUCCESS(0, "ok"),

    // 40xxx: 客户端错误
    PARAMS_ERROR(40000, "请求参数错误"),
    EMPTY_MESSAGE(40100, "消息不能为空"),
    MESSAGE_TOO_LONG(40101, "消息超过长度限制"),
    CONTENT_BLOCKED(40200, "请求包含不支持的词汇"),
    IMAGE_TOO_LARGE(40201, "图片尺寸超过限制"),
    IMAGE_FORMAT_INVALID(40202, "不支持的图片格式"),
    UNSUPPORTED_MEDIA_TYPE(40203, "不支持的多媒体类型"),

    // 50xxx: 服务端错误
    AI_AUTH_FAILED(50000, "AI 服务鉴权失败"),
    AI_RATE_LIMIT(50001, "AI 服务请求过于频繁"),
    AI_TIMEOUT(50002, "AI 服务响应超时"),
    AI_MODEL_UNAVAILABLE(50003, "AI 模型暂不可用"),
    MEMORY_ERROR(50010, "对话记忆异常"),
    IMAGE_GENERATION_FAILED(50020, "图片生成失败"),
    IMAGE_ANALYSIS_FAILED(50021, "图片分析失败"),
    GALLERY_OPERATION_FAILED(50040, "图库操作失败"),
    PROFILE_OPERATION_FAILED(50050, "图片画像操作失败"),
    SYSTEM_ERROR(59999, "系统内部异常");
}
```

**设计原则**：码段分段管理，4xxxx 客户端可自行修正重试，5xxxx 服务端错误建议稍后重试。

## BusinessException —— 唯一业务异常类

```java
throw new BusinessException(ErrorCode.EMPTY_MESSAGE);
throw new BusinessException(ErrorCode.CONTENT_BLOCKED, "消息包含违规词汇: xxx");
throw new BusinessException(ErrorCode.PARAMS_ERROR, "自定义详情");
```

**为什么不用受检异常？** Spring 的声明式事务对受检异常不默认回滚。BusinessException 继承 RuntimeException，`@Transactional` 默认回滚。

## ThrowUtils —— 统一断言入口

```java
ThrowUtils.throwIf(condition, ErrorCode.XXX);
ThrowUtils.throwIf(condition, ErrorCode.XXX, "详情");
```

**设计意图**：代码中统一用 `ThrowUtils.throwIf()` 抛异常，不直接 `new BusinessException(...)`。好处：
1. 代码语义清晰："条件成立则抛异常"
2. 避免遗漏 import BusinessException
3. 统一异常抛出口，方便全局搜索定位

## GlobalExceptionHandler

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public BaseResponse<?> handleBusiness(BusinessException e) {
        // → ResultUtils.error(e.getCode(), e.getMessage())
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public BaseResponse<?> handleValidation(MethodArgumentNotValidException e) {
        // @Valid 校验失败 → 字段名: 错误信息
        // → ResultUtils.error(40000, "字段: 校验失败")
    }

    @ExceptionHandler(Exception.class)
    public BaseResponse<?> handleException(Exception e) {
        // → ResultUtils.error(59999, "系统错误")
    }
}
```

**关键约束**：不返回 `ResponseEntity`，不设 `@ResponseStatus`。HTTP 状态码始终 200，业务状态在 JSON 的 `code` 字段。

### 异常兜底修复 (Phase 1)

**ExceptionGuardAdvisor 顺序修复**：getOrder() 从 `Integer.MAX_VALUE` 改为 `Integer.MIN_VALUE`，使其成为 Advisor 链中最外层。

修复前：ExceptionGuard 最后执行，try/catch 只包住模型调用，前面 Advisor 的 BusinessException 全部穿透逃逸。

修复后：ExceptionGuard 最先执行，兜住所有 Advisor 的异常→友好文案。

**双层兜底策略**：外层 ExceptionGuard（Advisor 链异常）+ 内层 ChatServiceImpl.onErrorResume（流式包装异常），互补覆盖。

## BaseResponse —— 统一响应包装

```java
@Data
@NoArgsConstructor  // ★ 必须保留，否则 Jackson 反序列化失败
public class BaseResponse<T> implements Serializable {
    private int code;       // 0=成功，40xxx=客户端错误，50xxx=服务端错误
    private T data;         // 成功时有数据，错误时为 null
    private String message; // "ok" / 错误信息
}
```

## ResultUtils —— 响应构建

```java
ResultUtils.success(data)              → {code:0, data:..., message:"ok"}
ResultUtils.error(ErrorCode.XXX)       → {code:40000, data:null, message:"..."}
ResultUtils.error(ErrorCode.XXX, "详情") → {code:40000, data:null, message:"详情"}
```

## Controller 方法签名规范

```java
// 非流式
@PostMapping
public BaseResponse<ChatResponseVO> chat(@Valid @RequestBody ChatRequest request)

// 流式 SSE（不能用 BaseResponse 包）
@PostMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<StreamEventVO> chatStream(@Valid @RequestBody ChatRequest request)
```

- 入参统一 `@Valid @RequestBody`
- 非流式返回 `BaseResponse<VO>`，通过 `ResultUtils.success()` 包装
- 流式返回 `Flux<StreamEventVO>`，错误通过流内 `{type:"error"}` 传递

## 分层返回值约定

| 层 | 返回什么 | 是否包 BaseResponse |
|----|---------|-------------------|
| Controller | `BaseResponse<VO>` | ✅ Controller 负责包装 |
| Service | 裸 VO / Entity | ❌ 不碰 BaseResponse |
| Repository | Entity / List<Entity> | ❌ 不碰 BaseResponse |

这样 Controller -> Service -> Repository 的数据流不携带 HTTP 层概念。
