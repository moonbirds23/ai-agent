# RAG 系统性学习手册

> 本文从面试和实际项目两个维度，系统梳理 RAG 的核心知识点。既包含当前项目已落地的实践（标注 ✅），也包含面试中常考的扩展话题。

---

## 一、什么是 RAG

### 1.1 核心定义

**RAG = Retrieval-Augmented Generation（检索增强生成）**

一句话：**不让 LLM 凭空编造，而是先检索相关文档/数据，再基于检索结果生成回答。**

```
用户提问 "帮我生成赛博朋克风格的夜景图"
    │
    ├─→ 向量检索：在图片库中找语义最相似的参考图
    ├─→ 元数据过滤：按标签/分类/风格筛选
    ├─→ 重排序：加权打分，取 Top-K
    └─→ 拼到 Prompt 里：LLM 看着参考图信息生成 imagePrompt
```

### 1.2 为什么需要 RAG

| LLM 的问题 | RAG 的解法 |
|-----------|-----------|
| **幻觉**：不知道的信息会编造 | 检索真实数据，基于事实回答 |
| **知识截止**：训练数据有截止日期 | 检索外部知识库，实时更新 |
| **不可溯源**：生成结果无法追溯来源 | 返回引用来源，可验证 |
| **领域知识缺失**：通用模型不懂专业领域 | 检索领域文档，专业知识增强 |
| **微调成本高**：数据变了要重新训练 | 只需更新知识库，无需重新训练 |

### 1.3 RAG vs 微调（面试高频）

| 维度 | RAG | 微调 |
|------|-----|------|
| 知识更新 | 实时更新知识库 | 需重新训练 |
| 可解释性 | 可追溯检索来源 | 黑盒 |
| 幻觉控制 | 基于检索事实，幻觉少 | 可能记忆错误训练数据 |
| 成本 | 检索+推理（每query） | 训练成本高，推理成本低 |
| 适用场景 | 知识频繁变化的场景 | 风格/格式固定的场景 |
| 两者关系 | **互补而非替代**：RAG 负责知识，微调负责行为 |

## 二、RAG 架构演进

### 2.1 Naive RAG（朴素 RAG）

最简单的三步：**索引 → 检索 → 生成**

```
文档 → 分块 → Embedding → 向量库
                         ↓
查询 → Embedding → 相似度检索 → Top-K 文档 → 拼接 Prompt → LLM 生成
```

**朴素 RAG 的三大痛点**：

| 痛点 | 表现 | 解法方向 |
|------|------|---------|
| **检索质量低** | 召回不相关文档、漏召回 | Query Rewrite / 混合检索 / 重排序 |
| **生成质量差** | 幻觉、上下文窗口溢出 | 上下文压缩 / 引用标注 |
| **系统不可控** | 检索结果不稳定 | 缓存 / 降级策略 |

### 2.2 Advanced RAG（增强 RAG）✅ 当前项目层级

在 Naive RAG 的检索前后增加处理环节：

```
查询 → [Query Rewrite] → [混合检索] → [重排序] → [上下文压缩] → LLM
         ↑ 改写优化        ↑ 多路召回     ↑ 精排       ↑ 去噪截断
```

**这正是当前项目的架构**：

| 环节 | 项目实现 | 作用 |
|------|---------|------|
| Query Rewrite | `RagQueryRewriteServiceImpl` | LLM 将用户需求改写为结构化检索条件 |
| 混合检索 | `HybridGalleryRetrieverImpl` | 向量(语义) + 关键词(标签) + 元数据(分类/风格) |
| 重排序 | `RagRerankerImpl` | 三路加权 + min-max 归一化 |
| 上下文压缩 | `RagContextPackerImpl` | referenceMode 裁剪 + 2500 字符截断 |

### 2.3 Modular RAG（模块化 RAG）

将 RAG 各环节模块化，按场景自由组合：

```
                    ┌─→ Query Rewrite ─┐
                    │                   ↓
用户查询 ──→ 路由 ──┤              向量检索 ──→ 重排序 ──→ 压缩 ──→ LLM
                    │                   ↑
                    └─→ 关键词提取 ────┘
                            ↑
                    [缓存层 / 降级策略 / 知识图谱]
```

**模块化 RAG 的关键模式**：

| 模式 | 说明 | 面试要点 |
|------|------|---------|
| **路由分发** | 根据查询类型，分发到不同的检索器 | 意图识别 → 不同索引 |
| **多路融合** | 向量 + 关键词 + 知识图谱多路并行，结果合并 | Recall 优先，Precision 靠后处理 |
| **迭代检索** | 第一次结果不理想 → 用 LLM 改写查询 → 再检索 | Self-RAG / CRAG（纠正性 RAG） |
| **图谱增强** | 在知识图谱中做实体链接，补充结构化知识 | GraphRAG（微软 2024） |

## 三、RAG 核心环节详解

### 3.1 文档索引（Ingestion）

```
原始文档 → 分块(Chunking) → Embedding → 向量库
              ↓
          元数据提取 → 结构化存储
```

**关键决策**：

| 维度 | 选项 | 权衡 |
|------|------|------|
| **分块大小** | 小(256) vs 大(1024) | 小：检索精准但丢失上下文；大：完整但噪声多 |
| **分块策略** | 固定大小 / 句子级 / 语义级 | 语义级最好但计算成本高 |
| **重叠度** | 0% / 10% / 20% | 防止关键信息被切在边界 |
| **元数据** | 标签/来源/时间/作者 | 用于过滤和加权 |

**当前项目**：图片索引单位为"图片 AI 画像"，`indexText` 约 500~2000 字，包含名称/简介/标签 + 视觉分析结果（主体/风格/色彩/构图/光影/氛围）。

### 3.2 Query Rewrite（查询改写）✅

**为什么需要**：用户表达不精确 → LLM 转换为更适合检索的 query。

```
用户输入: "来张赛博朋克风的"     → searchQuery: "赛博朋克风格夜景城市"
用户输入: "跟上次一样"           → 结合对话历史补全 → "古装人物水墨画风格"
用户输入: [上传了一张图，无文字]   → 视觉模型提取特征 → "古建筑、雪景、对称构图"
```

**常见改写策略**：

| 策略 | 说明 |
|------|------|
| 扩展改写 | 从短 query 扩展为详细描述 |
| 分解改写 | 复杂问题拆分为多个子问题检索 |
| 抽象改写 | 反推用户意图，生成抽象检索词 |
| HyDE | 先让 LLM 生成假设性答案，用答案的 embedding 去检索 |

### 3.3 检索策略（Retrieval）✅

#### 3.3.1 向量检索（语义检索）

```
query → Embedding 模型 → 向量 → 余弦相似度计算 → Top-K
```

**关键参数**：
- **Embedding 模型**：当前用智谱 `embedding-2`，维度 1024
- **相似度度量**：余弦距离（cosine_distance）
- **minScore 阈值**：0.4（embedding-2 相似度偏低）
- **索引类型**：IVFFlat（pgvector）

**面试点**：为什么是 0.4 而不是 0.7？不同 embedding 模型的相似度分布不同，embedding-2 的中文语义相似度通常在 0.4~0.5。阈值需要根据实际召回率/精确率曲线标定。

#### 3.3.2 关键词检索（稀疏检索）

```
query → 关键词提取 → 标签/名称匹配 → 打分
```

**当前项目**：标签完全匹配 +10，部分匹配 +5，名称包含检索词 +5。

#### 3.3.3 混合检索（Hybrid Retrieval）✅

向量（语义）+ 关键词（精确）两路召回，取并集后重排序。目的是互补：
- 向量擅长"意思相近"（赛博朋克 → 霓虹灯夜景）
- 关键词擅长"完全相同"（精确标签匹配）

#### 3.3.4 各种检索算法对比

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 向量检索 | Embedding + 余弦相似度 | 语义理解好，跨语言 | 黑盒，不可解释 |
| BM25 | 词频-逆文档频率 | 精确匹配，可解释 | 无语义理解 |
| 混合检索 | 向量 + BM25 融合 | 兼顾语义和精确 | 融合权重需调优 |
| ColBERT | Token 级交互检索 | 比单向量更精细 | 存储开销大 |
| 图谱检索 | 实体链接 + 子图检索 | 处理复杂关系推理 | 知识图谱构建成本高 |

### 3.4 重排序（Rerank）✅

**为什么需要**：初检（粗排）量大质量杂，需要精排提升 Top-K 质量。

```
粗排: 20 个候选（向量 + 关键词）
  ↓ 重排序（加权打分）
精排: 5 个最终结果
```

**当前项目的重排序公式**（Phase 1 已归一化）：

```
finalScore = (vectorScore/maxVector) × 50
           + (keywordScore/maxKeyword) × 15
           + (metadataScore/maxMetadata) × 10
```

**面试核心点**：归一化的必要性。三个分值量纲不同 → 不归一化的话，分数量纲大的维度会主导排序。详见 [架构决策记录 2](../02-架构设计/架构决策记录-异常并发与算法权衡.md#决策-2rerank-多维度分数的量纲归一化)。

**重排序的其他常用方法**：

| 方法 | 说明 |
|------|------|
| 规则加权 ✅ | 按固定权重线性加权（当前项目） |
| Cross-Encoder | 用 BERT-like 模型对 query-document pair 打分，比 Bi-Encoder 更准但更慢 |
| LLM-as-Ranker | 让 LLM 直接对比候选，输出排序 |
| MMR | 最大边际相关性，平衡相关性和多样性 |

### 3.5 上下文压缩与 Prompt 装配（Context Packing）✅

**为什么需要**：
- LLM 上下文窗口有限
- 检索到的文档质量参差不齐
- 注入无关信息 → LLM 输出变差（"Lost in the Middle"效应）

**当前项目策略**：
1. **referenceMode 裁剪**：overall → 全字段；style → 仅风格+氛围；color → 仅色彩+光影
2. **字符截断**：2500 字符上限，先截 retrieved（优先级低），再截 explicit（优先级高）
3. **模板装配**：`generation_with_rag.st` 渲染后注入 Prompt

## 四、RAG 评估体系

### 4.1 核心评估指标

| 维度 | 指标 | 含义 |
|------|------|------|
| **检索质量** | Recall@K | Top-K 结果中包含正确答案的比例 |
| **检索质量** | Precision@K | Top-K 结果中正确答案的比例 |
| **检索质量** | MRR | 第一个正确答案的平均倒数排名 |
| **检索质量** | NDCG | 考虑排序位置的归一化折损累计增益 |
| **生成质量** | Faithfulness | 生成内容与检索文档的一致性 |
| **生成质量** | Relevance | 生成内容与问题的相关性 |
| **系统性能** | 端到端延迟 | query → 回答的总耗时 |
| **系统性能** | 检索延迟 | 向量检索 + 重排序耗时 |

### 4.2 评估框架

| 框架 | 适用场景 |
|------|---------|
| RAGAS | Python 生态，自动化评估 retrieval + generation 质量 |
| TruLens | 带可视化 Dashboard 的评估和追踪 |
| LangSmith | LangChain 生态的追踪和评估平台 |
| 人工评估 | 最终质量判断，成本高但最可信 |

## 五、RAG 常见挑战与解法

### 5.1 检索失败（Retrieval Failure）

| 问题 | 根因 | 解法 |
|------|------|------|
| 漏召回（Low Recall） | query 与文档表述不一致 | Query Rewrite / 同义词扩展 / 多路召回 |
| 误召回（Low Precision） | 向量相似 ≠ 内容相关 | minScore 阈值 / 重排序 / 元数据过滤 |
| Top-K 不相关 | 检索质量差 | 增大候选集（oversample）后重排序 ✅ |
| 知识库覆盖不全 | 缺少相关文档 | 补全知识库 / 降级到纯 LLM 兜底 |

### 5.2 生成失败（Generation Failure）

| 问题 | 根因 | 解法 |
|------|------|------|
| 幻觉 | LLM 忽略检索结果 | 强化 Prompt 指令 / Self-RAG 自检 |
| 上下文窗口溢出 | 检索文档太多太长 | 上下文压缩 / 截断 ✅ |
| Lost in the Middle | LLM 倾向于用开头结尾信息 | 重排序把最重要的放最前面 |
| 答案不忠实于文档 | LLM 自由发挥 | Citation（强制引用来源） |

### 5.3 系统层面

| 问题 | 解法 |
|------|------|
| 检索延迟高 | 向量索引优化 / 候选缓存 / 预计算 |
| 知识库更新延迟 | 增量索引 / 实时写入 ✅（入库即建索引） |
| 多用户权限隔离 | 检索时按 userId/spaceId 过滤 |
| 成本不可控 | 熔断 / 限流 ✅ / 降级策略 |

## 六、RAG 面试常见专题

### 6.1 为什么 RAG 中的 Embedding 模型和 LLM 要用不同的模型？

- Embedding 模型专注将文本映射到语义向量空间，衡量的是**语义相似度**
- LLM 专注**文本生成和推理**
- 分离的好处：各自选最优模型，独立扩展，不相互影响
- 当前项目：embedding-2（嵌入）+ glm-4-flash（生成/改写），物理分离

### 6.2 如何处理 RAG 检索不到结果的情况？

分层降级：
1. 第二路召回 → 关键词搜索 fallback
2. 兜底策略 → 风格模板匹配（当前项目 Layer 3）
3. 纯 LLM 回答（不带检索上下文，标注"未找到相关参考"）
4. 引导用户提供更多信息

### 6.3 RAG 中如何处理多轮对话？

- 用 ChatMemory 维护对话历史
- Query Rewrite 时注入最近 N 轮对话（当前项目取 20 条）
- 要点：Rewrite 的输入是"[历史对话] + [当前 query]"，输出是独立于历史的检索 query

### 6.4 向量数据库选型

| 数据库 | 适用场景 | 当前选择 |
|--------|---------|---------|
| pgvector | 已有 PG，小规模，事务一致性要求高 | ✅ |
| Milvus | 大规模，分布式，高性能检索 | 未来扩展 |
| Qdrant | 中等规模，Rust 实现，性能好 | 备选 |
| Weaviate | 自带 Embedding 和 Schema | 快速原型 |
| Chroma | Python 生态，轻量 | 非 Java 场景 |

**选型理由**：pgvector 与业务数据库同库，减少运维复杂度。IVFFlat 在万级数据量下够用。后续可迁移。

### 6.5 RAG 和 Agent 的关系

- **RAG** 是 Agent 的"知识插件"——Agent 调用工具时，RAG 是最常用的检索工具之一
- **Agent 扩展了 RAG**：Agent 可以自主决定"什么时候检索"、"检索什么"、"检索结果是否够用"
- **Self-RAG**：LLM 在生成过程中自我评估是否需要检索、检索结果是否相关，不相关就重新检索

## 七、当前项目的 RAG 体系总结

```
当前级别: Advanced RAG（增强 RAG） ✅

✅ 已实现:
  Query Rewrite          → LLM 改写查询，提取结构化检索条件
  混合检索                → 向量(pgvector) + 关键词(标签/名称) + 元数据(分类/风格/色彩/构图)
  重排序                  → 三路加权 + 批次内 min-max 归一化
  上下文压缩              → referenceMode 裁剪 + 2500 字符截断
  三层兜底                → Layer1(显式图) → Layer2(RAG检索) → Layer3(模板)
  多路降级                → 向量失败 → 关键词 fallback → 模板兜底
  评估追踪                → RagTrace 记录全链路（rewrite→candidates→selected→latency）
  全局开关                → app.rag.enabled
  熔断超时                → Query Rewrite 30s 超时
  检索抽象                → ReferenceRetriever 接口（面向接口扩展）
  对话理解                → Query Rewrite 注入最近 20 条对话历史
  图→图检索              → 上传图无文字 → 视觉模型提取特征 → 作为检索 query

⬜ 未实现（面试时可讨论的扩展方向）:
  Cross-Encoder 重排序    → 比规则加权更精准的语义重排序
  Self-RAG               → LLM 自检是否需要检索、结果是否够用
  知识图谱增强            → 图片→实体→关系→推理
  多模态 RAG             → 直接用图片 embedding 检索（而非图→文→检索）
  结果引用标注            → 生成的 imagePrompt 标注参考了哪张图
  RAG 评估体系           → 自动化 Recall/Precision/Faithfulness 评估
```
