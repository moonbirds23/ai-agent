# RAG 中如何实现向量数据库的增量更新？

> 标签: RAG, 向量数据库, 增量更新, 索引维护 | 难度: 🟡 中等 | 编号: QA25

---

## 一、核心结论

RAG 中向量数据库的增量更新，是指当原始文档发生新增、修改、删除时，不每次全量重建知识库，而是只处理发生变化的文档或 chunk，并同步更新**文本、向量、元数据、倒排索引和 ANN 索引**。

主流工程链路是：

```text
数据源变更检测
  ↓
计算文档 hash / 版本号
  ↓
只解析变化文档
  ↓
重新分块并生成 chunk_id
  ↓
新增 / 更新 / 删除 chunk 向量和 metadata
  ↓
维护索引、缓存和引用映射
  ↓
评估召回质量和线上指标
```

核心原则：**用稳定 ID 和版本控制保证可追踪，用 hash 判断变更，用 upsert/delete 做局部更新，用评测和索引维护保证质量。**

---

## 二、为什么需要增量更新

全量重建适合初始化或大版本迁移，但日常生产环境通常需要增量更新。

| 场景 | 说明 |
|------|------|
| 新文档加入 | 新制度、新产品文档、新 FAQ 发布 |
| 文档修改 | 原文内容、标题、权限、版本、更新时间变化 |
| 文档删除 | 过期文档、撤回文档、权限失效 |
| 局部更新 | 只改了某一页、某一节、某个表格 |
| Embedding 模型未变 | 只需更新变化 chunk，不必全量重算 |

如果没有增量更新能力，知识库会出现数据过期、检索不一致、引用失效和运维成本过高的问题。

---

## 三、增量更新的主流实现流程

### 3.1 数据源变更检测

常见方式包括：

| 方式 | 适用场景 |
|------|----------|
| 文件更新时间 / 版本号 | 文件系统、对象存储、企业网盘 |
| 内容 hash | 判断文档内容是否真实变化 |
| 数据库 CDC / binlog | 业务数据库、知识库表 |
| 消息队列事件 | 文档发布系统、CMS、审批流 |
| 定时扫描 | 简单系统或无事件通知的数据源 |

推荐至少保存：

```text
doc_id
source_uri
content_hash
metadata_hash
updated_at
parser_version
embedding_model_version
index_version
```

这样可以判断是否需要重新解析、重新向量化或只更新 metadata。

### 3.2 稳定生成 doc_id 和 chunk_id

增量更新的关键是 ID 稳定。

```text
doc_id = hash(source_uri 或业务主键)
chunk_id = hash(doc_id + section_path + chunk_index 或 chunk_content_hash)
```

设计时要权衡：

- 如果 `chunk_id` 只依赖顺序，文档前面插入一段会导致后面所有 chunk ID 改变；
- 如果 `chunk_id` 依赖内容 hash，相同内容更容易复用，但引用映射和顺序关系需要额外维护；
- 对有章节结构的文档，`section_path + 局部序号` 通常比全局序号更稳定。

### 3.3 新增文档：insert / upsert

新增文档流程：

```text
解析文档 → 清洗 → 分块 → Embedding → upsert(chunk_id, content, vector, metadata)
```

同时写入：

- 向量索引；
- BM25 / 全文索引；
- metadata 表；
- 文档版本表；
- 引用和权限相关字段。

### 3.4 修改文档：diff 后局部更新

修改文档不一定要删除所有旧 chunk。常见做法：

1. 重新解析新版本文档；
2. 生成新的 chunk 列表；
3. 对比旧 chunk 和新 chunk；
4. 未变化 chunk 复用；
5. 变化 chunk 重新 embedding 并 upsert；
6. 删除新版本中不存在的旧 chunk。

```text
old_chunks = {A, B, C}
new_chunks = {A, B', D}

A 复用
B → B' 重新向量化并更新
C 删除
D 新增
```

### 3.5 删除文档：软删除优先

删除有两种策略：

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| 软删除 | 设置 `deleted=true` 或 `status=inactive`，检索时过滤 | 需要审计、可恢复、合规留痕 |
| 硬删除 | 直接删除向量和元数据 | 数据撤回、隐私删除、节省存储 |

生产系统通常先软删除，再由清理任务异步硬删除和压缩索引。

## 四、索引维护要点

### 4.1 向量库通常支持增量写入，但质量仍需监控

很多向量数据库支持 upsert/delete，但这不代表索引质量永远不需要维护。

以 pgvector 为例，HNSW 和 IVFFlat 索引会随 INSERT/UPDATE/DELETE 维护；但如果数据分布明显变化、删除更新频繁、IVFFlat 在数据量较小时创建，可能需要 `ANALYZE`、`REINDEX` 或重新评估索引参数。

因此更严谨的说法是：**增量写入解决数据同步问题，索引维护解决长期性能和召回质量问题。**

### 4.2 Embedding 模型变更通常需要全量重建

如果只是文档内容变化，可以增量更新；但如果 Embedding 模型、向量维度、归一化方式或距离度量发生变化，通常需要全量重新向量化。

```text
embedding-2 1024维 → 新模型 1536维
=> 旧向量和新向量不在同一向量空间，不能混用
```

此时应建立新索引版本，灰度切换，而不是直接覆盖旧库。

### 4.3 保持向量索引和关键词索引一致

如果系统使用混合检索，更新时不能只更新向量库，还要同步更新 BM25 / 全文索引。

```text
chunk upsert
  ├─ vector_store upsert
  ├─ keyword_index upsert
  ├─ metadata_store upsert
  └─ cache invalidate
```

否则可能出现向量检索命中新内容，但关键词检索仍返回旧内容，导致结果不一致。

## 五、工程落地架构

### 5.1 批处理型增量更新

适合日更、小时级更新的知识库。

```text
定时任务
  ↓
扫描变更文档
  ↓
批量解析 / embedding
  ↓
批量 upsert / delete
  ↓
更新索引版本和统计指标
```

优点是实现简单、成本可控；缺点是实时性一般。

### 5.2 事件驱动型增量更新

适合知识更新频繁、实时性要求较高的系统。

```text
文档发布事件 / CDC / MQ
  ↓
Ingestion Worker
  ↓
解析、分块、向量化
  ↓
upsert/delete
  ↓
通知缓存失效和评测监控
```

优点是实时性好；缺点是要处理幂等、重试、乱序、失败补偿和死信队列。

### 5.3 双索引灰度切换

适合大规模重建或模型升级。

```text
旧索引 index_v1 在线服务
新索引 index_v2 后台构建
  ↓
评测通过
  ↓
流量灰度切换到 index_v2
  ↓
保留 v1 回滚窗口
```

这比直接原地覆盖更安全。

## 六、常见风险和处理

| 风险 | 处理方式 |
|------|----------|
| 重复写入 | upsert 幂等，使用稳定 chunk_id |
| 更新一半失败 | 任务状态表、重试、事务或补偿机制 |
| 旧 chunk 残留 | diff 后删除不存在的旧 chunk，或按 doc_id 批量清理 |
| 引用失效 | 保存文档版本和 source_uri，前端提示历史引用版本 |
| 权限变化未同步 | metadata 更新必须触发索引和缓存失效 |
| 分块策略变化 | 视为索引版本变化，必要时全量重建 |
| 模型变更 | 新建向量空间和索引版本，不混用旧向量 |

## 七、面试回答模板

> RAG 中向量数据库的增量更新一般从数据源变更检测开始，可以通过更新时间、内容 hash、版本号、CDC 或消息队列判断文档是否变化。对新增文档，解析、清洗、分块后生成 embedding，然后按 chunk_id upsert 到向量库和关键词索引；对修改文档，最好重新解析新版本并和旧 chunk 做 diff，未变化的 chunk 复用，变化的 chunk 重新向量化，不存在的旧 chunk 删除或软删除；对删除文档，通常先软删除并在检索时过滤，再异步硬删除。工程上要保证 doc_id 和 chunk_id 稳定，记录 parser_version、embedding_model_version 和 index_version，并同步更新 metadata、权限和 BM25 索引。需要注意的是，增量写入不等于永远不用维护索引，数据分布变化、删除频繁或索引性能下降时仍要 ANALYZE、REINDEX 或重建；如果更换 Embedding 模型或向量维度，通常需要全量重新向量化并灰度切换新索引。
