# 向量数据库的工作流程有哪些？请简述下

> 标签: 向量数据库 | 难度: 🟡 中等 | 编号: QA16

---

## 一、两大阶段

向量数据库的典型工作流程可以分为两个阶段：离线/准实时的索引构建（写入路径），以及在线查询检索（读取路径）。

```text
┌─────────────────────────────────────────────────────┐
│  写入路径：数据入库与索引构建                          │
│                                                       │
│  原始数据 → 清洗/解析 → 分块 → Embedding → 向量+元数据  │
│                                      ↓                │
│                              写入向量库 / 构建 ANN 索引 │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  读取路径：在线查询与结果后处理                         │
│                                                       │
│  用户查询 → Query Rewrite → Embedding → ANN 检索       │
│                                      ↓                │
│                         过滤 / Rerank / 上下文组装      │
└─────────────────────────────────────────────────────┘
```

主流 RAG 系统通常还会在检索结果之后增加 Rerank、上下文压缩、引用映射和安全兜底，使向量数据库不仅“查得快”，也“查得准、可解释、可追踪”。

---

## 二、写入路径：数据入库与索引构建

### 步骤 1：数据解析与预处理

对原始数据进行解析、清洗、结构化和质量控制。输出通常是文本片段和元数据。

常见处理包括：

- 解析 PDF、Word、网页、表格、图片 OCR 等来源；
- 清理页眉页脚、HTML 噪声、乱码、广告文本；
- 提取标题、章节、页码、URL、更新时间、权限、业务标签等元数据；
- 去重和近重复检测，避免检索结果被重复内容占据。

### 步骤 2：分块（Chunking）

将长文档切分为适合检索和注入上下文的 chunk。

```text
长文档 → 按标题/段落/语义边界切分 → chunk + metadata
```

分块大小会影响召回质量和生成质量：块过大容易带入噪声，块过小可能丢失上下文。工程上常结合 chunk overlap、章节路径和相邻 chunk 回填来保持语义完整性。

### 步骤 3：向量化（Embedding）

将每个 chunk 通过 Embedding 模型转换为固定维度向量。

```text
文本: “赛博朋克夜景，霓虹灯与雨中街道”
  → embedding 模型
  → [0.23, -0.45, 0.78, ..., 0.56]
```

关键约束是：同一检索空间中的文档向量和查询向量必须使用兼容的 Embedding 模型、维度和归一化方式。更换 Embedding 模型后，通常需要重新向量化和重建索引。

### 步骤 4：写入向量库

向量库通常保存三类信息：

```text
chunk_text + embedding_vector + metadata
```

以 pgvector 为例，可以把向量存储在 PostgreSQL 表中：

```sql
INSERT INTO picture_vector_store (id, content, metadata, embedding)
VALUES (uuid, '赛博朋克夜景...', '{"pictureId": 42}', '[0.23, -0.45, ...]');
```

metadata 对 RAG 很关键，后续可用于权限过滤、时间过滤、业务分类、引用溯源和调试追踪。

### 步骤 5：构建或维护 ANN 索引

为了提升检索性能，向量库通常会构建 ANN 索引，例如 IVFFlat 或 HNSW。

```sql
-- IVFFlat: 聚类倒排索引
CREATE INDEX ON picture_vector_store
  USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 100);

-- HNSW: 图索引
CREATE INDEX ON picture_vector_store
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
```

需要修正一个常见说法：向量索引并不一定“不能实时更新”。在 PostgreSQL/pgvector 中，索引会随 INSERT/UPDATE/DELETE 维护；但 IVFFlat 如果在数据量很少时创建，聚类质量可能不稳定，数据分布发生明显变化后也可能需要 `ANALYZE`、`REINDEX` 或重新建库评估。不同向量数据库对增量写入、删除和索引维护的机制不同，不能一概而论。

## 三、读取路径：在线查询检索

### 步骤 1：查询预处理与改写

用户问题可能短、含糊或依赖上下文。主流 RAG 会在检索前做 Query Rewrite 或 Query Expansion：

```text
原始问题: “它怎么优化？”
改写后: “RAG 系统如何通过检索、重排序和上下文压缩优化回答质量？”
```

如果是企业知识库，还可能提取结构化过滤条件，例如部门、时间范围、文档类型或权限范围。

### 步骤 2：查询向量化

使用与文档入库兼容的 Embedding 模型将查询转换为向量：

```text
用户输入: “未来感城市夜景”
  → embedding 模型
  → [0.19, -0.42, 0.81, ..., 0.51]
```

### 步骤 3：向量检索与元数据过滤

查询向量在 ANN 索引中查找近似最近邻，同时结合 metadata 做过滤。

```sql
SELECT id, content, metadata, embedding <=> query_vector AS distance
FROM picture_vector_store
WHERE metadata @> '{"category": "city"}'
ORDER BY embedding <=> query_vector
LIMIT 20;
```

pgvector 中 `<=>` 表示 cosine distance。距离越小通常表示越相似；如果需要相似度分数，可以按具体度量转换，例如 `1 - cosine_distance`。

### 步骤 4：候选后处理

检索结果通常不会直接全部注入 Prompt，而会经过后处理：

- **阈值过滤**：过滤低相关候选；
- **去重**：删除重复或近重复 chunk；
- **Rerank**：用 Cross-Encoder、LLM 或规则权重重新排序；
- **上下文压缩**：只保留与问题相关的句子或段落；
- **引用映射**：为每个可引用 chunk 分配系统编号；
- **权限校验**：确保用户只能看到有权限访问的内容。

### 步骤 5：组装给生成模型

最终注入 LLM 的通常不是原始 Top-K，而是结构化上下文：

```text
[1] 来源: doc-a, p.12, score=0.86
内容: ...

[2] 来源: doc-b, section=3.1, score=0.82
内容: ...
```

生成阶段再结合拒答策略、引用约束和输出格式要求生成答案。

## 四、关键运维操作

| 操作 | 说明 |
|------|------|
| 增量写入 | 新向量写入后通常会被索引维护，但召回质量仍需监控 |
| 索引维护 | 数据分布变化大、删除更新频繁或性能退化时，考虑 `ANALYZE`、`REINDEX` 或重建索引 |
| Embedding 模型变更 | 维度或向量空间变化后，通常需要全量重新向量化和重建索引 |
| 元数据治理 | metadata 决定过滤、权限和引用能力，不能只存文本和向量 |
| 质量评估 | 通过 Recall@K、MRR、人工标注集和线上反馈评估检索效果 |
| 可观测性 | 监控查询延迟、Top-K 命中、低分率、空检索率、Rerank 前后差异 |

## 五、主流默认方案与增强方案

### 5.1 主流默认方案

```text
文档清洗 → 分块 → Embedding → 写入向量库（文本+向量+metadata）
用户查询 → Query Rewrite → Embedding → ANN Top-K → 阈值过滤 → Rerank → 上下文组装
```

这是多数 RAG 系统的默认工程链路，适用于企业知识库、客服问答、文档问答和语义搜索。

### 5.2 高可信/特定场景增强方案

- 引入混合检索：向量检索 + BM25/关键词检索；
- 引入权限感知检索：先过滤权限或在检索层做租户隔离；
- 构建离线评测集：持续评估 Recall@K、引用准确率和拒答准确率；
- 对高风险答案做断言验证和引用支撑校验；
- 对多知识库场景增加路由、RRF 融合和跨库去重。

## 六、面试回答模板

> 向量数据库的流程可以分为写入路径和读取路径。写入路径包括文档解析清洗、分块、提取元数据、调用 Embedding 模型生成向量，然后把文本、向量和 metadata 写入向量库，并构建 HNSW 或 IVFFlat 等 ANN 索引。读取路径是用户查询先做必要的改写，再用同一个向量空间的 Embedding 模型向量化，通过 ANN 检索 Top-K 候选，并结合元数据过滤、阈值过滤、去重、Rerank 和上下文压缩得到最终上下文。工程上要注意 Embedding 模型一致性、索引参数调优、权限过滤、引用溯源和可观测性；更换 Embedding 模型通常需要全量重建向量库。
