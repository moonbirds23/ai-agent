# RAG 系统如何标注信息来源和提供引用？

> 标签: RAG, 引用溯源, 可信生成 | 难度: 🟡 中等 | 编号: QA19

---

## 一、一句话回答

RAG 的引用能力不是生成阶段临时产生的，而是从文档入库开始保留 chunk 级元数据，检索时返回来源信息，Prompt 注入前由系统分配引用编号，模型只能选择这些编号进行标注，生成后再做引用合法性校验和前端溯源展示。

核心原则是：**引用编号由系统控制，来源信息来自检索 metadata，模型只能选择可用引用，不能自行生成来源。**

---

## 二、为什么 RAG 需要引用

引用主要解决三个问题：

| 目标 | 说明 |
|------|------|
| 可信度 | 用户可以看到答案依据，而不是只看到模型生成结果 |
| 可验证性 | 用户能点击来源文档、页码、章节或原文片段进行核对 |
| 幻觉控制 | 模型被约束在检索证据范围内回答，降低无证据生成风险 |

没有引用的 RAG 更接近“搜索增强聊天”；具备引用和溯源能力的 RAG 才更适合企业知识库、法务、医疗、金融、合规等严肃场景。

---

## 三、整体流程

```text
文档解析
  ↓
分块 Chunking
  ↓
保存 chunk 文本 + 向量 + metadata
  ↓
检索返回 chunk + score + metadata
  ↓
系统为检索片段分配 citation_id
  ↓
Prompt 中注入带编号的参考资料
  ↓
LLM 回答时只能选择给定编号，如 [1][2]
  ↓
后处理校验引用并生成前端溯源数据
```

核心点：引用依赖 chunk 级元数据，而不是只依赖原始文档名。文档名只能说明来源范围，chunk 才能说明具体证据片段。

---

## 四、第一步：入库时保存来源元数据

每个 chunk 入库时，除了保存文本和向量，还要保存可追溯的来源字段。

常见元数据包括：

| 字段 | 作用 |
|------|------|
| `doc_id` | 原始文档唯一 ID |
| `chunk_id` | 文档分块唯一 ID |
| `title` | 文档标题 |
| `source_url` | 原文 URL 或文件地址 |
| `page` | PDF / Word 页码 |
| `section` | 章节标题或层级路径 |
| `author` / `department` | 作者、部门或知识库归属 |
| `published_at` / `updated_at` | 发布时间或更新时间 |
| `permission_scope` | 权限、租户或可见范围 |
| `score` | 检索阶段产生的相关性分数 |

示例：

```json
{
  "chunk_id": "spring-ai-doc-001#p12-c3",
  "doc_id": "spring-ai-doc-001",
  "title": "Spring AI Reference",
  "source_url": "https://docs.spring.io/spring-ai/reference/",
  "page": 12,
  "section": "ChatClient Advisors",
  "updated_at": "2025-05-20"
}
```

如果入库阶段没有保存这些 metadata，后续就很难稳定提供引用，只能依赖模型根据文本内容推测来源，容易产生假引用。

---

## 五、第二步：检索时携带来源信息

向量库或检索服务返回的结果不能只有文本，还要包含 score 和 metadata：

```text
检索结果 = chunk_text + score + metadata
```

例如：

```json
{
  "content": "Advisor 可以在 ChatClient 调用前后拦截请求和响应。",
  "score": 0.87,
  "metadata": {
    "source_id": "doc-1#p12-c3",
    "title": "Spring AI Reference",
    "page": 12,
    "section": "Advisors",
    "source_url": "https://docs.spring.io/spring-ai/reference/"
  }
}
```

检索层应同时完成权限过滤和可见性校验，避免模型引用用户无权访问的资料。

---

## 六、第三步：系统分配引用编号

在注入 Prompt 前，系统将候选 chunk 编号，而不是让模型自行命名来源。

```text
[1] 来源: Spring AI Reference, p.12, section=Advisors
内容: Advisor 可以在 ChatClient 调用前后拦截请求和响应。

[2] 来源: Spring AI API Guide, p.8, section=Memory
内容: MessageChatMemoryAdvisor 可以将对话历史注入模型上下文。
```

同时维护映射关系：

```text
citation_id → chunk_id → doc_id → source_url / page / section
```

然后在系统提示词中约束模型：

```text
请仅基于给定参考资料回答。
如果使用了某条资料，请在句子末尾标注来源编号，如 [1]、[2]。
如果资料不足，请回答“基于当前知识库无法确定”。
不要引用未提供的来源编号。
不要自行生成文档名、URL 或页码。
```

这一步的关键是：引用编号由系统控制，模型只能选择，不负责创造来源。

---

## 七、第四步：答案中输出引用标记

模型回答示例：

```text
Spring AI 的 Advisor 可以在 ChatClient 调用前后拦截请求和响应 [1]。
MessageChatMemoryAdvisor 可以将历史对话注入上下文，从而支持多轮记忆 [2]。
```

引用标注常见形式：

| 形式 | 示例 | 适用场景 |
|------|------|----------|
| 编号引用 | `Advisor 支持请求拦截 [1]` | 最常见，便于前端映射 |
| 脚注引用 | `Advisor 支持请求拦截¹` | 报告、论文式回答 |
| 行内来源 | `根据《Spring AI Reference》第 12 页...` | 法务、政策、制度类问答 |

工程上最常用编号引用，因为它便于和检索结果列表、来源卡片、原文跳转建立稳定映射。

---

## 八、第五步：后处理校验引用

生成后应做引用校验，避免模型输出不存在、不匹配或不支撑结论的引用。

### 8.1 校验引用编号是否合法

检查答案中的 `[1] [2]` 是否都在系统提供的引用编号范围内。

```text
检索结果只有 [1][2][3]
模型输出 [4] → 删除、标记为无效引用或触发重生成
```

这是最小可用实现中也应包含的校验。

### 8.2 校验引用是否支撑答案

更严格的做法是做句子级或断言级校验：

```text
答案句子 → 对应引用 chunk → 判断该 chunk 是否支持该句子
```

如果句子和引用内容无关，需要删除引用、降低置信度、改写答案，或重新生成。

### 8.3 合并重复来源

多个 chunk 可能来自同一篇文档。展示时可以合并为同一来源下的多个片段：

```text
[1] Spring AI Reference, p.12
[2] Spring AI Reference, p.13
```

也可以在前端展示为同一文档卡片下的多个命中片段，减少来源列表冗余。

---

## 九、前端如何展示引用

前端一般会把引用做成可点击来源：

```text
回答正文：
Advisor 可以拦截请求和响应 [1]。

来源：
[1] Spring AI Reference / Advisors / p.12
    原文片段：Advisor can intercept requests and responses...
    查看原文：打开文档链接
```

常见展示方式：

- 答案中的 `[1]` 可点击，高亮右侧来源卡片；
- 来源卡片展示标题、页码、章节、相关片段和更新时间；
- PDF 跳转到具体页码，网页跳转到原始 URL；
- 企业知识库跳转到内部文档详情页，并遵守权限控制；
- 高可信场景展示引用片段与答案句子的对应关系。

## 十、最小可用实现与高可信增强实现

### 10.1 最小可用实现

适合普通企业知识库、内部助手和低风险问答：

```text
入库保存 doc_id/chunk_id/title/url/page
检索返回 content + metadata
系统分配 [1][2][3]
Prompt 要求模型只能引用给定编号
后处理检查编号是否合法
前端展示来源卡片
```

最小实现的重点是让引用来源可追踪，避免模型自由生成来源。

### 10.2 高可信增强实现

适合法务、医疗、金融、合规、政策制度等严肃场景：

- 句子级引用：每个关键断言至少绑定一个来源；
- 引用支撑校验：判断引用 chunk 是否真的支持该句子；
- 断言抽取 + 反向检索验证；
- 多来源冲突检测，冲突时显式说明；
- 来源可信度排序，例如官方文档优先、更新时间新的文档优先；
- 可审计 trace：记录检索、重排、上下文压缩、引用编号映射和校验结果。

高可信实现能显著提升可验证性，但会增加成本、延迟和系统复杂度，因此应根据业务风险选择。

## 十一、常见问题和坑

### 11.1 模型可能伪造引用

如果让模型自己生成“来源名称”、URL 或页码，它可能生成不存在的文档。因此引用编号必须由系统预先提供，并限制模型只能使用这些编号。

### 11.2 引用了不代表被支持

模型可能在一句话后面标了 `[1]`，但 `[1]` 的内容并不能支撑这句话。高可信场景要做引用支撑校验。

### 11.3 chunk 太碎会导致引用不完整

如果分块过小，单个 chunk 可能缺少上下文，用户点开引用后难以理解。可以在展示时带上前后相邻 chunk，或保留章节路径。

### 11.4 来源排序不等于引用顺序

检索结果 Top-1 不一定被答案引用，答案引用顺序也不一定等于检索排序。工程上应维护 `citation_id → chunk_id` 的映射，而不是依赖数组位置临时推断。

### 11.5 权限过滤不能只放在前端

如果用户无权访问某个文档，后端检索和引用构造阶段就应过滤掉该来源。否则模型可能泄露受限信息，即使前端不展示来源卡片也不安全。

## 十二、面试回答模板

> RAG 的引用能力要从入库阶段开始设计。文档切成 chunk 时，需要保存 doc_id、chunk_id、标题、URL、页码、章节、更新时间和权限等 metadata；检索时返回的不只是文本，还要带上 metadata 和相关性分数。然后系统在 Prompt 注入前为候选 chunk 分配 [1]、[2]、[3] 这样的引用编号，并维护 citation_id 到 chunk_id 和原文地址的映射。模型只负责选择这些编号进行标注，不能自行生成文档名、URL 或页码。生成后至少要校验引用编号是否合法，高可信场景还要做句子级引用支撑校验和断言验证。最后前端把编号映射成可点击来源卡片，展示原文片段、文档标题、页码或链接。核心原则是引用由系统控制，来源来自检索 metadata，模型只能选择不能创造。

## 十三、追问点

**Q: 引用来源应该在什么时候生成？**

> 来源元数据在文档入库和分块时保存；引用编号通常在检索结果注入 Prompt 前由系统生成；最终展示引用在生成后由后处理和前端完成。

**Q: 为什么不能让模型自己写来源？**

> 因为模型可能生成不存在的文档名、页码或 URL，形成假引用。正确做法是系统给定可引用的编号和 metadata，模型只能选择这些编号。

**Q: 如何判断一个引用是否真的支撑答案？**

> 最小做法是检查引用编号是否合法；严格做法是把答案拆成事实断言或句子，再判断对应 chunk 是否能支撑该断言，不能支撑的句子应删除、改写或标低置信度。

**Q: 多个来源冲突怎么办？**

> 可以按来源可信度、更新时间和业务优先级排序；如果冲突无法自动解决，答案中应明确说明“资料存在冲突”，分别列出不同来源，而不是合成一个没有证据支持的确定结论。

## 十四、项目实践参考

在当前 `ai-agent` 项目里，类似思想可以落在：

- 图库图片和画像文本入库时保存 `pictureId`、名称、分类、标签、来源 URL 等元数据；
- RAG 检索结果保留图片 ID、图片名称、画像摘要和相关性分数；
- `PromptReferenceAssembler` / Context Pack 阶段将参考图信息结构化注入 Prompt；
- `ragDebugInfo` 可作为调试溯源数据返回前端，帮助查看命中了哪些参考图以及为什么命中。
