# 什么是提示压缩？为什么在 RAG 中需要提示压缩？

> 标签: RAG, 上下文优化 | 难度: 🟢 简单 | 来源: 面试鸭

---

## 一、一句话定义

把检索到的大量文档内容压缩成 LLM 能高效理解的精简形式，在不超出上下文窗口的前提下保留关键信息。

---

## 二、为什么需要（三个原因）

### 原因 1：上下文窗口有限

即使 128K 窗口的模型，注入内容太多也会导致：
- **注意力稀释**：信息越多，LLM 对每条信息的关注度越低
- **成本线性增长**：Token 计费，注入越多越贵
- **延迟增加**：更长 Prompt → 更慢推理速度

### 原因 2：检索文档质量参差

检索回来的文档不是 100% 相关，每条文档可能只有几句话有用，其余是噪声。全文塞入会让 LLM 在噪声中找信号。

### 原因 3："Lost in the Middle" 效应

LLM 倾向于关注 Prompt 的开头和结尾，中间部分容易被忽略。最相关的文档如果排在中间位置，LLM 可能根本没注意到。

---

## 三、五种压缩策略

### 策略 1：字段裁剪

检索文档有多字段，不是所有字段都需要。根据用户意图只保留相关字段。

```
用户关心风格 → 只保留 style/mood 字段
用户关心构图 → 只保留 composition 字段
```

| 延迟 | 精度损失 | 复杂度 |
|------|---------|--------|
| 零 | 低 | 低 |

### 策略 2：字符截断

设置最大字符数上限，超限截断，优先级低的先截。

```
检索到 2500 字，限制 1500 字
  → 先截低排名文档
  → 再截高排名文档的尾部
```

| 延迟 | 精度损失 | 复杂度 |
|------|---------|--------|
| 零 | 中 | 低 |

### 策略 3：LLM 摘要压缩

用 LLM 将每条文档提炼为一句话摘要，只注入摘要而非全文。

```
原始: "这是一张赛博朋克夜景图，紫色和青色霓虹灯，雨中街道，仰视构图..."
摘要: "[图库#42] 赛博朋克夜景 | 紫色+青色 | 仰视 | 孤独氛围"
```

| 延迟 | 精度损失 | 复杂度 |
|------|---------|--------|
| 高（需 LLM 调用） | 低~中 | 中 |

### 策略 4：重排序 + 前置 + 截断

先 Rerank 把最相关文档排前面，再截断一刀切掉后面的。

```
Rerank 前: [0.4] [0.9] [0.3] [0.8]
Rerank 后: [0.9] [0.8] [0.4] [0.3]
                          ↑ 从这截断
注入 LLM: [0.9] [0.8]
```

| 延迟 | 精度损失 | 复杂度 |
|------|---------|--------|
| 低 | 低~中 | 低 |

### 策略 5：增量压缩

长文本分多次压缩：每条单独压缩 → 合并后再整体压缩 → 最终精简文本。

| 延迟 | 精度损失 | 复杂度 |
|------|---------|--------|
| 很高 | 最低 | 高 |

---

## 四、策略对比总览

| 策略 | 延迟 | 精度损失 | 实现复杂度 |
|------|------|---------|-----------|
| 字段裁剪 | 零 | 低 | 低 |
| 字符截断 | 零 | 中 | 低 |
| LLM 摘要压缩 | 高 | 低~中 | 中 |
| 重排序 + 截断 | 低 | 低~中 | 低 |
| 增量压缩 | 很高 | 最低 | 高 |

---

## 五、面试速记

> 提示压缩 = 检索结果太多了，得精简一下再给 LLM 看。
>
> 三个原因：上下文窗口有限、检索文档有噪声、LLM 看中间容易走神（Lost in the Middle）。
>
> 五种策略从简到繁：字段裁剪、字符截断、重排后截断、LLM 摘要压缩、增量压缩。实际项目中通常组合使用。
