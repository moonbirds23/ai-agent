# 什么是 RAG 中的 Rerank？具体需要怎么做？

> 标签: RAG, 检索, 重排序 | 难度: 🟡 中等 | 编号: QA9

---

## 一、核心定义

Rerank（重排序）是 RAG 检索链路中的精排阶段。初检阶段通常为了保证召回，会从向量检索、BM25 或混合检索中取较多候选；Rerank 再对候选进行二次评分、排序、去冗余和截断，只把最适合生成回答的 Top-K 证据注入上下文。

```
用户问题
  ↓
初检召回 Top-20 / Top-50        # 偏召回，允许混入噪声
  ↓
Rerank / 去重 / 多样性控制       # 偏精度，筛掉低价值候选
  ↓
最终 Top-3 / Top-8 注入 Prompt  # 控制上下文质量和成本
```

Rerank 的目标不是“多拿几条文档”，而是提升最终上下文的相关性、可信度、覆盖度和可用性。

---

## 二、为什么需要 Rerank

### 2.1 初检和精排目标不同

| 阶段 | 目标 | 候选数量 | 典型方法 | 容忍问题 |
|------|------|----------|----------|----------|
| 初检 Retrieval | 高召回、低延迟 | 20~100 | 向量检索、BM25、混合检索 | 可以包含噪声 |
| 精排 Rerank | 高精度、强相关 | 3~10 | Cross-Encoder、规则融合、MMR、LLM Ranker | 尽量减少无关证据 |

初检追求“不漏”，Rerank 追求“放进 Prompt 的每条都有价值”。

### 2.2 单一相似度分数不足以代表答案价值

向量相似度通常只衡量语义接近程度，但真实业务排序还会受到以下因素影响：

- 文档版本是否最新；
- 用户是否有权限访问；
- 文档类型是否匹配；
- 是否包含答案所需实体、时间、数值或代码符号；
- 是否与其他候选重复；
- 是否满足业务规则中的强过滤或软偏好。

因此，Rerank 往往要融合语义相关性、关键词匹配、元数据、业务规则和多样性，而不是只看一个向量分。

### 2.3 控制上下文噪声和 Lost in the Middle

LLM 对长上下文的利用并不均匀，关键信息如果被噪声包围或放在中间位置，可能被忽略。Rerank 可以把最相关、最可靠的证据排在更靠前的位置，并减少重复片段，提升生成阶段的可用信息密度。

## 三、主流 Rerank 方案与适用场景

### 3.1 业务规则融合：稳定、低成本、强可控

业务规则融合通常把元数据、权限、时间、版本、分类、标签等信号引入排序。它在生产系统中很常见，但更准确地说，它是“业务相关性和合规约束”的融合层，不等价于语义精排模型。

常见做法：

```
finalScore = semanticScore_norm * w1
           + keywordScore_norm  * w2
           + metadataScore_norm * w3
           + businessBoost      * w4
```

| 信号 | 示例 | 作用 |
|------|------|------|
| 语义分 | 向量相似度、Cross-Encoder 分数 | 判断内容是否回答问题 |
| 关键词分 | BM25、标题命中、实体命中 | 弥补专有名词、编号、代码符号 |
| 元数据分 | 文档类型、时间、版本、部门、语言 | 提升业务匹配度 |
| 业务规则 | 权限、收藏、置顶、最新版本优先 | 满足产品和合规约束 |

适用场景：

- 元数据质量较高，例如企业文档、图库、商品、工单、知识库；
- 需要明确业务偏好或强约束，例如“只看最新版本”“只看已授权文档”；
- 对延迟敏感，无法对大量候选运行模型精排。

工程注意点：

1. 不同分数必须归一化，否则量纲大的分数会主导排序。
2. 强约束应优先做过滤，而不是只做加权。例如权限、租户、合规状态不应靠加分解决。
3. 权重需要通过评测集或线上 A/B 调整，不能只靠经验固定。
4. 规则融合适合表达业务偏好，但对复杂语义匹配的提升有限。

### 3.2 Cross-Encoder / Reranker 模型：主流语义精排方案

Cross-Encoder 会把 query 和 document 拼在一起输入模型，由模型直接输出相关性分数。与双塔向量检索相比，它能建模 query-document 之间更细粒度的 token 交互，因此通常精度更高。

```
候选文档 d_i
  ↓
CrossEncoder(query, d_i)
  ↓
相关性分数 score_i
  ↓
按 score_i 排序并截断
```

| 优点 | 代价 |
|------|------|
| 语义判断能力强，适合精排 | 每个 query-doc pair 都要前向推理 |
| 对同义、否定、细节匹配更敏感 | 候选集过大时延迟明显增加 |
| 主流开源和商业模型成熟 | 需要模型部署、批处理和监控 |

适用场景：

- 问答准确率优先，能够接受额外几十到数百毫秒延迟；
- 初检候选数量可控，常见为 20~100 条以内；
- 候选文本长度适中，能放入 reranker 模型输入窗口；
- 有明确评测集，能验证 reranker 是否带来收益。

工程实践中，Cross-Encoder 通常不是替代初检，而是接在初检之后：先用向量或混合检索快速召回，再用 reranker 精排少量候选。

### 3.3 MMR：相关性与多样性的平衡

MMR（Maximal Marginal Relevance，最大边际相关性）不是严格意义上的语义精排模型，而是一种结果选择策略。它在选择高相关候选的同时，惩罚与已选结果过于相似的候选，避免最终 Top-K 被重复内容占满。

```
MMR(d) = λ * relevance(d, query)
       - (1 - λ) * max similarity(d, selected_docs)
```

| 适合场景 | 不适合场景 |
|----------|------------|
| 多文档总结、对比分析、需要覆盖多个方面 | 只需要最精确单一答案的事实问答 |
| 同一文档相邻 Chunk 重复较多 | 候选本身召回质量很低 |
| 需要减少同质证据占满上下文 | 强业务排序优先级高于多样性时 |

MMR 的代价较低，不需要额外 LLM 调用，但它主要解决“去冗余”和“覆盖面”问题，不能替代 Cross-Encoder 的深度语义判断。

### 3.4 LLM-as-Ranker：强语义判断，但成本最高

LLM-as-Ranker 是把候选列表或候选摘要交给大模型，让模型判断哪些证据最相关，甚至输出排序理由。

常见形式：

```
给定用户问题和候选片段列表，请按“是否能支持回答”排序，并说明保留原因。
```

| 优点 | 代价 / 风险 |
|------|-------------|
| 能利用复杂推理、业务语境和自然语言解释 | 延迟和 token 成本高 |
| 适合少量候选的高价值查询 | 排序稳定性受 Prompt 和模型影响 |
| 可同时做证据检查、冲突识别和摘要 | 候选过多时上下文和费用不可控 |

适用场景：

- 候选数量较少，例如 Cross-Encoder 或规则先筛到 5~20 条；
- 查询价值高，例如法律、投研、复杂故障分析；
- 需要模型解释为什么保留或排除某些证据；
- 可以接受更高延迟和成本。

LLM-as-Ranker 通常作为增强方案或高价值请求的二级精排，不宜作为所有请求的默认路径。

## 四、方案对比与组合关系

| 方案 | 主要解决问题 | 精度 | 延迟 / 成本 | 可解释性 | 典型定位 |
|------|--------------|------|-------------|----------|----------|
| 业务规则融合 | 元数据、权限、时间、版本、业务偏好 | 中 | 低 | 高 | 业务约束和低成本排序 |
| Cross-Encoder / Reranker | query-doc 细粒度语义相关性 | 高 | 中 | 中 | 主流语义精排 |
| MMR | 去冗余、多样性覆盖 | 中 | 低 | 中 | Top-K 选择与上下文多样性控制 |
| LLM-as-Ranker | 复杂语义判断、证据解释、冲突识别 | 高到很高 | 高 | 中到高 | 高价值查询增强精排 |

推荐组合方式：

```
1. 强过滤：租户、权限、状态、时间范围等不可违反条件
2. 初检召回：向量检索 / BM25 / 混合检索，取 Top-20~100
3. 规则融合：处理业务偏好、版本、新鲜度、标题命中等信号
4. Cross-Encoder：对候选做语义精排，提升答案相关性
5. MMR / 去重：减少重复 Chunk，保证覆盖多个证据点
6. 可选 LLM-as-Ranker：仅对高价值或复杂问题做最终证据筛选
```

这比“规则加权最常用”更准确：规则融合常用于业务排序和低成本控制，Cross-Encoder 是更典型的语义 reranker；MMR 解决多样性，不直接提升语义判断；LLM-as-Ranker 是高成本增强项。

## 五、工程落地要点

### 5.1 分数归一化

不同检索器和规则分数的量纲不同。BM25 分数、向量相似度、标签命中数不能直接相加，通常需要 min-max、z-score、rank-based normalization 或 RRF。

### 5.2 候选数量控制

Rerank 的延迟通常与候选数量线性相关。常见做法是：

```
初检 Top-50 → 规则过滤 / 粗排 Top-30 → Cross-Encoder Top-10 → MMR Top-5
```

### 5.3 强过滤与软排序分离

权限、租户、合规状态、文档可见性应作为强过滤条件；“更喜欢最新版本”“收藏优先”“标题命中加分”可以作为软排序信号。

### 5.4 可观测性和评测

需要记录每个阶段的候选、分数、排序变化和最终注入内容。评测指标包括 Recall@K、MRR、nDCG、答案正确率、引用命中率、平均延迟和 token 成本。

## 六、常见误区

| 误区 | 更准确的说法 |
|------|--------------|
| Rerank 就是规则加权 | 规则融合只是 Rerank 的一种低成本实现，语义精排通常依赖 Cross-Encoder 或 reranker 模型 |
| Cross-Encoder 可以直接检索全库 | Cross-Encoder 计算成本高，通常只能对初检后的少量候选做精排 |
| MMR 能替代 Reranker | MMR 主要解决去重和多样性，不擅长复杂语义相关性判断 |
| LLM-as-Ranker 效果最好所以应默认使用 | 它成本和延迟最高，适合高价值、少候选、复杂判断场景 |
| 分数直接相加即可 | 不同分数必须归一化或转成排名，否则融合结果不可靠 |

---

## 七、面试回答模板

Rerank 是 RAG 中初检之后、生成之前的精排阶段。初检通常为了召回会拿 20 到 100 条候选，但最终放进 Prompt 的只有几条，所以需要 Rerank 来提升相关性、去掉噪声和重复内容。工程上我会把 Rerank 拆成几类：第一类是业务规则融合，用于处理权限、时间、版本、标签、标题命中等低成本可控信号；第二类是 Cross-Encoder 或专门的 reranker 模型，这是主流语义精排方案，适合对少量候选做 query-doc 细粒度匹配；第三类是 MMR，用于在相关性之外控制多样性，避免重复 Chunk 占满上下文；第四类是 LLM-as-Ranker，语义判断和解释能力强，但成本和延迟高，通常只用于高价值或复杂查询。落地时要注意强过滤和软排序分离、分数归一化、候选数量控制，并用 Recall@K、MRR、nDCG、答案正确率和延迟成本做评估。
