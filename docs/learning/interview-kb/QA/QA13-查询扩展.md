# 什么是查询扩展？为什么在 RAG 应用中需要查询扩展？

> 标签: RAG, 检索优化 | 难度: 🟡 中等 | 编号: QA13

---

## 一、核心定义

查询扩展（Query Expansion）是在检索前或检索过程中，对用户原始查询补充更多有助于召回的表达，例如同义词、领域术语、缩写全称、上下文指代、相关实体或假设性答案，从而提升检索覆盖率。

在 RAG 中，查询扩展主要解决两个问题：

1. 用户查询通常很短，语义信息不足；
2. 用户表达和知识库表达可能不一致，存在词汇鸿沟。

需要注意，查询扩展不等于无条件把查询变长。扩展过度会引入错误意图和噪声，因此必须控制范围，并通过评测验证收益。

---

## 二、查询扩展、查询改写和历史补全的关系

这些概念经常被混用，面试中应区分清楚。

| 方法 | 核心动作 | 主要目标 | 主流程度 |
|------|----------|----------|----------|
| Query Rewrite | 改写原始查询表达 | 让查询更清晰、更适合检索 | 主流做法 |
| 历史补全 | 用对话上下文补全省略和指代 | 解决多轮问答中的“它”“上一个”等问题 | 主流做法 |
| Query Expansion | 增加同义词、术语、相关表达 | 扩大召回覆盖 | 常见做法 |
| Self-Query | 提取结构化过滤条件 | 将自然语言约束转成 metadata filter | 主流增强做法 |
| HyDE / PRF / KG 扩展 | 生成假设文档、伪反馈、图谱邻居 | 复杂召回增强 | 增强方案，按需使用 |

工程上，最常见的默认链路通常是：先做历史补全和 Query Rewrite，再做向量或混合检索；同义词扩展、自查询、HyDE、PRF、知识图谱扩展则根据场景和成本逐步叠加。

---

## 三、为什么需要查询扩展

### 3.1 查询过短或信息稀疏

用户可能只输入：

```
“报销流程”
“RAG 优化”
“接口超时”
```

这些查询缺少上下文、版本、业务线和具体问题描述，直接 embedding 后语义向量可能不够稳定。适度扩展可以增加检索信号。

### 3.2 词汇不匹配

| 用户表达 | 文档表达 | 问题 |
|----------|----------|------|
| 自动驾驶 | 无人驾驶、智能驾驶 | 同义词不一致 |
| RAG | 检索增强生成、Retrieval-Augmented Generation | 缩写和全称不一致 |
| 向量数据库 | Vector Database、Vector Store | 跨语言表达不一致 |
| 报销 | 费用报销、差旅报销、费用申请 | 业务术语粒度不一致 |

查询扩展可以把这些等价或相关表达补入检索过程，提高召回概率。

### 3.3 多轮对话中的省略和指代

```
历史：用户问“Spring AI 的 Advisor 链怎么工作？”
当前：用户问“它和 Filter 有什么区别？”

补全后：Spring AI 的 Advisor 链和传统 Filter 有什么区别？
```

在多轮 RAG 中，历史补全通常比泛泛地扩展同义词更重要，因为当前问题可能根本不是一个完整检索 query。

## 四、主流工程做法

### 4.1 Query Rewrite：默认优先方案

Query Rewrite 用 LLM 或规则将用户问题改写成更适合检索的表达，重点是消除口语、省略和歧义。

```
原始查询：这个怎么配置？
历史上下文：用户正在讨论 Spring AI PgVectorStore
改写后：Spring AI PgVectorStore 如何配置数据库连接和向量维度？
```

适用场景：

- 多轮对话；
- 用户表达口语化或不完整；
- 需要把复杂问题拆成更明确的检索意图；
- 希望降低直接扩展带来的噪声。

工程注意点：改写后的 query 应保留用户原始意图，不能引入未出现的业务约束或结论。

### 4.2 历史补全：多轮 RAG 的基础能力

历史补全使用最近若干轮对话，将代词、省略词和上下文主题补全。

```
历史：
  用户：介绍一下混合检索
  助手：混合检索结合向量检索和 BM25……
当前：
  用户：它和自查询有什么区别？
补全：
  混合检索和自查询有什么区别？
```

适用条件：

- 有会话记忆；
- 当前问题依赖上文；
- 检索系统不能直接理解“它”“上面那个”“继续”等指代。

历史补全属于主流必备能力，但需要控制历史窗口，避免旧话题污染当前查询。

### 4.3 同义词和术语扩展：低成本、可控

同义词扩展可以基于词典、领域术语表、缩写表或人工维护的映射。

```
RAG → 检索增强生成 / Retrieval-Augmented Generation
向量库 → Vector Database / Vector Store
工单 → ticket / issue / service request
```

适用场景：

- 领域术语相对稳定；
- 缩写、别名、内部黑话较多；
- 对可解释性和低延迟要求高。

局限是维护成本较高，而且词典无法理解具体上下文。例如“Apple”在不同领域可能指公司，也可能指水果。

### 4.4 Multi-Query Retrieval：生成多个检索 query

由 LLM 为同一问题生成多个不同角度的检索表达，分别检索后合并去重。

```
原始问题：如何减少 RAG 幻觉？
扩展查询：
  1. RAG 如何做引用校验？
  2. 检索增强生成如何降低 hallucination？
  3. RAG 答案无依据时如何拒答？
```

适用场景：

- 原问题较宽泛；
- 知识库表达多样；
- 需要提高召回覆盖。

代价是检索次数增加，且多个查询可能带来重复候选，需要融合和去重。

## 五、增强方案：按需使用

### 5.1 Self-Query：结构化条件提取

Self-Query 从自然语言中提取 metadata filter，例如时间、分类、来源、标签。

```
用户：找 2024 年发布的 Spring AI 官方文档
输出：
  searchQuery = "Spring AI 官方文档"
  filter = { year: 2024, sourceType: "official" }
```

它常与 Query Rewrite 合并在一次 LLM 调用中完成。适用前提是知识库有可靠元数据 schema，并且服务端会校验 filter。

### 5.2 知识图谱扩展：实体关系驱动

知识图谱扩展会识别查询中的实体，并沿图谱关系补充相关实体或概念。

```
Transformer → Self-Attention → Multi-Head Attention → BERT / GPT
```

适用场景：

- 实体关系明确，例如医学、金融、法律、科研、企业组织架构；
- 已有高质量知识图谱或实体库；
- 查询需要沿关系扩展。

代价是图谱建设和维护成本较高，不适合作为普通 RAG 系统的默认方案。

### 5.3 PRF：伪相关反馈

伪相关反馈（Pseudo Relevance Feedback）先做一次初检，再从 Top-N 结果中提取高频词、实体或摘要，回填到查询中进行二次检索。

```
查询：机器学习
初检结果出现：深度学习、监督学习、神经网络
扩展后：机器学习 深度学习 监督学习 神经网络
```

适用条件是初检结果质量较好。若初检本身偏了，PRF 会把错误方向进一步放大。

### 5.4 HyDE：假设文档嵌入

HyDE（Hypothetical Document Embeddings）先让 LLM 根据问题生成一个假设性答案或文档，再对该假设文档做 embedding 检索。

```
用户问题 → LLM 生成假设答案 → 对假设答案 embedding → 向量检索
```

HyDE 适合用户问题较抽象、直接 embedding 效果不佳的场景。代价是增加 LLM 调用，并且假设答案可能引入错误方向，因此需要后续 Rerank 和证据校验。

## 六、工程落地要点

1. **不要过度扩展**：扩展词越多不一定越好，过度扩展会引入噪声和意图漂移。
2. **保留原始查询**：扩展查询应与原始查询一起参与检索或日志记录，便于排查。
3. **扩展结果要可控**：限制扩展词数量、类别和长度，必要时要求 LLM 输出结构化 JSON。
4. **按场景选择方案**：多轮优先历史补全，短查询优先 Rewrite / Multi-Query，实体关系强再考虑 KG。
5. **结合混合检索和 Rerank**：扩展提高召回后，需要融合和精排控制噪声。
6. **评测驱动**：用 Recall@K、nDCG、MRR、答案正确率和延迟成本评估扩展收益。
7. **安全边界**：扩展不能绕过权限、租户、合规过滤；结构化 filter 必须由服务端校验。

## 七、常见误区

| 误区 | 更准确的说法 |
|------|--------------|
| 查询扩展就是加同义词 | 同义词只是其中一种，还包括 Rewrite、历史补全、Multi-Query、HyDE、PRF 等 |
| 扩展越多召回越好 | 扩展过多会引入噪声，降低精排和生成质量 |
| LLM 扩展一定优于词典 | LLM 灵活但有成本和不稳定性；领域词典低延迟、可控，适合稳定术语 |
| HyDE 是默认必选 | HyDE 是增强方案，适合抽象查询或直接 embedding 召回差的场景 |
| 历史越多补全越准确 | 过长历史可能引入旧话题污染，需要窗口控制和主题判断 |

---

## 八、面试回答模板

查询扩展是在检索前对用户查询补充或改写，使它更容易命中文档中的表达，主要解决短查询、词汇不匹配和多轮指代不完整的问题。工程上我会把主流做法和增强做法区分开：默认优先做 Query Rewrite 和历史补全，把“它、上一个、这个怎么配置”这类问题还原成完整检索 query；如果领域术语和缩写很多，可以叠加同义词词典或术语表；如果需要更高召回，可以用 Multi-Query 生成多个检索表达。知识图谱扩展、PRF 和 HyDE 属于增强方案，适合实体关系明确、初检质量较高或抽象查询较多的场景，但会增加成本、延迟或噪声。落地时要限制扩展长度，保留原始查询，结合混合检索和 Rerank，并用 Recall@K、nDCG、答案正确率和延迟成本评估效果。
