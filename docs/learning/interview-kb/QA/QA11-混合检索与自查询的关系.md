# 混合检索和自查询有什么区别？是处理同一件事吗？

> 标签: RAG, 检索 | 难度: 🟡 中等 | 编号: QA11

---

## 一、核心结论

混合检索（Hybrid Retrieval）和自查询（Self-Query）不是同一件事，它们解决的是 RAG 检索链路中不同阶段的问题。

- **自查询**：发生在检索前，负责把自然语言问题解析为“语义查询 + 结构化过滤条件”，解决“搜什么、过滤什么”。
- **混合检索**：发生在检索中，负责同时使用向量检索和关键词检索等多路召回，解决“怎么搜、用哪些检索器搜”。

二者是正交关系，可以单独使用，也可以组合使用。

```
用户问题
  ↓
Self-Query：解析语义 query 和 metadata filter
  ↓
Hybrid Retrieval：向量检索 + BM25 / 关键词检索
  ↓
融合去重 → Rerank → 生成
```

---

## 二、详细对比

| 维度 | 自查询（Self-Query） | 混合检索（Hybrid Retrieval） |
|------|----------------------|------------------------------|
| 主要目标 | 从自然语言中提取结构化检索意图 | 结合多种检索方式提升召回稳定性 |
| 所处阶段 | 检索前的查询解析 | 检索执行阶段 |
| 输入 | 用户自然语言问题、可用元数据 schema | 查询文本、过滤条件、检索器配置 |
| 输出 | 语义 query + metadata filter / sort / limit | 多路召回候选集合 |
| 典型技术 | LLM 结构化输出、规则解析、schema-aware prompting | Dense vector、BM25、倒排索引、RRF 融合 |
| 解决的问题 | 时间、分类、作者、权限、标签等结构化条件 | 向量和关键词各自的召回盲区 |
| 风险 | 过滤条件解析错误会导致漏召回 | 融合不当会引入噪声或排序偏差 |

---

## 三、自查询解决什么问题

自查询适合处理用户问题中隐含的结构化约束。例如：

```
用户：找一下 2024 年发布的、关于 Spring AI 的官方文档

Self-Query 输出：
  searchQuery: "Spring AI 官方文档"
  filter:
    publishYear = 2024
    sourceType = "official_doc"
```

如果没有自查询，系统可能只把整句话做向量检索，导致“2024 年”“官方文档”等约束没有被严格执行。

自查询常见输出包括：

- 时间范围：年份、月份、最近 N 天；
- 分类：文档类型、业务线、知识库；
- 作者 / 来源：官方、内部、外部、某部门；
- 标签：产品、版本、语言、状态；
- 排序偏好：最新、最高评分、最近更新；
- limit：用户明确要求“前 5 个”。

需要注意，权限、租户、合规状态等安全条件不应完全依赖 LLM 自查询生成，应由服务端强制追加。

---

## 四、混合检索解决什么问题

混合检索适合处理单一检索方式不稳定的问题。例如：

```
用户：API-2024-B 这个错误码怎么处理？

向量检索：可能认为 API-2024-B 与 API-2023-C 语义接近，排名不稳定
关键词检索：可以精确命中 API-2024-B
混合检索：同时保留语义候选和精确候选，再融合排序
```

它主要弥补：

- 向量检索对专有名词、编号、代码符号不敏感；
- 关键词检索无法处理同义词和模糊表达；
- 短查询或跨语言查询导致单路召回不足；
- 不同检索器对不同问题类型表现不同。

## 五、如何组合使用

### 5.1 组合链路

```
用户：我去年收藏的赛博朋克夜景图

1. Self-Query 解析：
   searchQuery = "赛博朋克夜景"
   filter = { year: 2025, favorited: true }

2. Hybrid Retrieval 执行：
   向量检索：searchQuery + filter
   关键词检索：searchQuery + filter

3. 融合与精排：
   合并去重 → RRF / 规则融合 → Rerank → Top-K
```

在这个例子里，自查询负责把“去年”“收藏”转成结构化过滤条件，混合检索负责用多路检索器召回候选。

### 5.2 与 Query Rewrite 的关系

Self-Query 可以看作 Query Rewrite 的一种结构化增强。普通 Query Rewrite 通常输出改写后的自然语言检索词；Self-Query 除了改写查询，还会输出过滤条件。

```
普通 Query Rewrite：
  { searchQuery: "赛博朋克夜景图片" }

Self-Query：
  {
    searchQuery: "赛博朋克夜景图片",
    filter: { favoritedOnly: true, year: 2025 },
    sort: { field: "updatedAt", order: "desc" }
  }
```

工程上可以在同一次 LLM 调用中同时完成历史补全、查询改写和结构化条件提取，但前提是元数据字段定义清晰，并且要对输出做校验。

## 六、工程落地要点

1. **明确 metadata schema**：自查询依赖可用字段定义，例如 `year`、`category`、`sourceType`、`favorited`。
2. **过滤条件要可验证**：LLM 输出的字段和值必须做白名单校验，不能直接拼 SQL 或过滤表达式。
3. **安全过滤服务端强制追加**：租户、权限、合规状态不能由 LLM 决定。
4. **混合检索要处理分数融合**：BM25 和向量分数不可直接比较，通常用 RRF 或归一化加权。
5. **自查询错误要有兜底**：当解析置信度低或 filter 过窄导致无结果时，可放宽过滤条件重试。
6. **记录解析和召回日志**：需要能追踪查询被改写成什么、过滤了什么、每路召回了哪些结果。

## 七、常见误区

| 误区 | 更准确的说法 |
|------|--------------|
| 自查询就是混合检索 | 自查询是检索前解析，混合检索是检索执行策略 |
| 有 Self-Query 就不需要 Hybrid Retrieval | Self-Query 不能解决向量和关键词的召回盲区 |
| 有 Hybrid Retrieval 就不需要 Self-Query | 混合检索不能自动严格执行时间、分类、权限等结构化条件 |
| LLM 生成的 filter 可以直接使用 | 必须做 schema 校验、类型校验和值域校验 |
| 所有约束都交给自查询 | 安全、租户、权限等约束必须由后端强制执行 |

---

## 八、面试回答模板

混合检索和自查询不是同一个概念，它们在检索链路中的位置不同。自查询发生在检索前，主要把用户自然语言中的结构化意图解析出来，比如时间、分类、来源、是否收藏等，输出语义 query 和 metadata filter；混合检索发生在检索执行阶段，是同时使用向量检索和 BM25 或关键词检索，弥补单一路径的召回盲区。工程上二者可以组合：先用 Self-Query 解析过滤条件，再在过滤条件约束下做向量和关键词双路召回，之后用 RRF、规则融合或 Rerank 得到最终 Top-K。需要注意的是，LLM 生成的过滤条件必须做 schema 校验，权限和租户隔离必须由服务端强制追加，不能完全交给模型。
