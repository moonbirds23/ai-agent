# 在 RAG 应用中为了优化检索精度，数据清洗和预处理怎么做？

> 标签: RAG, 索引, 数据清洗 | 难度: 🟡 中等 | 编号: QA12

---

## 一、核心结论

RAG 的检索质量很大程度上取决于索引数据质量。数据清洗和预处理的目标不是“把文本处理得更漂亮”，而是让进入向量库和倒排索引的内容具备语义完整性、结构一致性、可检索性和可追溯性。

工程上应区分两类工作：

- **基础必做的数据清洗**：格式解析、去噪、去重、结构修复、元数据抽取、权限字段保留。这些属于上线前必须完成的质量底座。
- **高级增强索引优化**：标题注入、上下文摘要、假想问答、HyDE、多向量索引、层级索引等。这些可以提升复杂场景召回，但会增加成本、延迟、存储和维护复杂度。

不能把所有增强手段都当作默认必选项。基础清洗优先保证数据正确，高级优化再根据评测结果逐步叠加。

---

## 二、基础必做：数据清洗和规范化

### 2.1 文档解析与格式标准化

不同来源文档需要先统一成可索引的文本和元数据结构。

| 来源 | 常见处理方式 | 注意点 |
|------|--------------|--------|
| PDF | PyMuPDF、pdfplumber、Unstructured、OCR | 区分文本型 PDF 和扫描件；保留页码与标题层级 |
| HTML | Readability、BeautifulSoup、DOM 解析 | 去除导航、广告、脚本、样式；保留正文结构 |
| Markdown | Markdown parser | 保留标题、列表、代码块和表格语义 |
| Office 文档 | Apache POI、LibreOffice、Unstructured | 注意表格、批注、页眉页脚和版本信息 |
| 图片 / 扫描件 | OCR 或多模态模型描述 | OCR 置信度低时需标记质量风险 |
| 音视频 | ASR + 章节切分 + 关键帧描述 | 需要时间戳，便于引用定位 |

标准化后的数据至少应包含：正文、标题、来源、页码或位置、更新时间、文档 ID、权限范围、语言、文档类型等字段。

### 2.2 去噪

去噪目标是移除无语义或会干扰检索的内容。

常见噪声包括：

- HTML 中的导航栏、版权声明、广告、脚本；
- PDF 中的页眉页脚、页码、水印、目录重复项；
- OCR 产生的乱码、断字、重复字符；
- 日志或代码文档中的模板化无效行；
- 过短、纯符号、纯数字或信息密度极低的片段。

示例清洗规则：

```python
import re

# 去除零宽字符和控制字符
text = re.sub(r'[​‌‍﻿]', '', text)
text = re.sub(r'[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]', '', text)

# 统一空白，但不要在需要保留换行结构的阶段过早压平
text = re.sub(r'[ \t]+', ' ', text)
```

需要注意：去噪不等于简单删除所有格式。标题、列表、表格、代码块和页码往往是检索和引用的重要结构信息，应尽量保留为结构化字段。

### 2.3 去重

重复内容会导致 Top-K 被同质片段占满，降低上下文利用率。

| 去重层级 | 方法 | 适用场景 |
|----------|------|----------|
| 文档级精确去重 | SHA-256 / MD5 | 文件重复上传、镜像文档 |
| 文档级近似去重 | SimHash、MinHash | 版本差异很小的文档 |
| 段落 / Chunk 去重 | MinHash、embedding 相似度、内容 hash | FAQ、制度条款、网页抓取内容 |
| 相邻 Chunk 去冗余 | overlap 检查、MMR | 分块重叠导致的重复召回 |

去重不能盲目删除所有相似内容。对制度、合同、法律条文这类版本敏感数据，应保留版本、发布时间和生效状态，通过元数据控制检索优先级。

### 2.4 结构修复和语义完整性

Embedding 和关键词检索都依赖较完整的语义单元。常见修复包括：

- 修复 PDF 硬换行，避免一句话被拆成多行；
- 合并被错误拆开的标题、列表和段落；
- 将表格转换为 Markdown 表格或键值对文本；
- 保留代码块语言和上下文说明；
- 将图片说明、图注、表注与正文建立关联；
- 对过长段落按语义边界切分。

表格处理示例：

```
原始表格：
| 模型 | 维度 | 最大输入 |
|------|------|----------|
| embedding-2 | 1024 | 512 token |

可索引文本：
模型 embedding-2 的向量维度是 1024，最大输入长度是 512 token。
```

如果直接把复杂表格压成无结构纯文本，Embedding 可能无法正确表达行列关系。

### 2.5 元数据抽取与保留

元数据不仅用于展示，也用于过滤、排序、权限控制和引用定位。基础元数据通常包括：

- 文档 ID、Chunk ID、来源 URL、文件路径；
- 标题、章节、页码、段落序号；
- 创建时间、更新时间、生效时间、版本；
- 文档类型、业务线、标签、语言；
- 租户、部门、角色、权限范围；
- 解析器版本、清洗版本、索引版本。

其中权限、租户、可见性字段属于强约束，必须保留到检索阶段，不能只放在展示层。

## 三、基础预处理流程

```
原始数据源
  ↓
文档解析：PDF / HTML / Markdown / Office / OCR / ASR
  ↓
格式标准化：正文 + 标题 + 结构 + 元数据
  ↓
去噪：页眉页脚、乱码、导航、广告、低信息片段
  ↓
去重：文档级、段落级、Chunk 级
  ↓
结构修复：断行、表格、列表、代码块、图文关系
  ↓
元数据抽取：来源、时间、权限、版本、页码、章节
  ↓
分块：按语义边界和 token 预算切分
  ↓
Embedding / BM25 索引 / 向量库入库
```

这条链路是 RAG 数据侧的基本功，通常比盲目更换 embedding 模型更优先。

## 四、高级增强：索引优化手段

高级增强不是每个项目都必须做，适合在基础清洗完成后，根据评测发现的召回问题定向引入。

### 4.1 标题和层级上下文注入

将标题、章节、文档类型等结构信息注入 Chunk 文本，使 Embedding 能感知上下文。

```
[文档] Spring AI 1.0 使用指南
[章节] VectorStore 配置
[正文] PgVectorStore 支持相似度检索和元数据过滤……
```

适用场景：Chunk 正文本身较短，离开标题后语义不完整。代价是 token 增加，且过度注入会引入重复噪声。

### 4.2 上下文摘要 / Contextual Retrieval

为每个 Chunk 生成简短上下文说明，例如它属于哪份文档、前后章节在讲什么，再与正文一起索引。

适用场景：长文档被切分后，单个 Chunk 缺少上下文。代价是需要额外 LLM 调用，并且摘要质量需要监控。

### 4.3 假想问答或问题索引

为每个 Chunk 生成可能被用户问到的问题，将“问题向量”和“正文向量”一起索引。

```
Chunk: embedding-2 的维度为 1024。
生成问题: embedding-2 的向量维度是多少？
```

适用场景：FAQ、产品文档、客服知识库。代价是索引量增加，且生成问题如果偏离正文会带来误召回。

### 4.4 多向量和多粒度索引

同一份文档可以建立多种索引：

- Chunk 向量：适合精确片段召回；
- 文档摘要向量：适合先定位文档；
- 标题 / 问题向量：适合短查询；
- BM25 倒排索引：适合专有名词和精确词项；
- 表格结构化索引：适合数值、字段查询。

适用场景：知识库规模大、文档类型复杂、查询类型多样。代价是存储、同步和融合排序复杂度上升。

### 4.5 HyDE、PRF 等查询侧增强的配合

HyDE、伪相关反馈（PRF）更偏查询侧增强，但会影响索引设计。例如如果系统大量使用 HyDE，需要保证索引文本保留足够语义描述；如果使用 PRF，需要初检索引具备较高基础召回质量。

这些方法属于增强项，不应掩盖基础清洗不合格的问题。

## 五、质量评估和监控

数据清洗不能只靠人工肉眼检查，应建立可量化指标：

| 指标 | 含义 |
|------|------|
| 解析成功率 | 文档是否成功转为可索引内容 |
| 有效文本比例 | 清洗后保留的有效正文占比 |
| 重复率 | 文档级和 Chunk 级重复比例 |
| Chunk 平均长度 / 方差 | 分块是否过短或过长 |
| 元数据完整率 | 标题、来源、权限、时间等字段是否缺失 |
| OCR 置信度 | 扫描件和图片文本质量 |
| Recall@K / nDCG | 数据处理后检索质量是否提升 |
| 引用可定位率 | 生成答案能否定位到页码、章节或 URL |

上线后还应保留清洗版本和索引版本，便于回滚和对比。

## 六、常见误区

| 误区 | 更准确的说法 |
|------|--------------|
| 数据清洗就是正则去噪 | 正则只是基础手段，还包括解析、结构修复、去重、元数据和权限保留 |
| 清洗越狠越好 | 过度清洗可能删除标题、表格、页码、代码等关键检索线索 |
| 高级增强越多越好 | 标题注入、假想问答、多向量会增加成本和噪声，应由评测驱动 |
| 换更强 Embedding 就能解决数据问题 | 低质量解析、重复和权限缺失通常无法靠模型完全弥补 |
| 所有重复内容都应删除 | 版本敏感或法规类文档应保留版本信息，通过元数据排序和过滤控制 |

## 七、面试回答模板

RAG 的数据清洗和预处理可以分成基础必做和高级增强两层。基础层首先要把 PDF、HTML、Markdown、Office、OCR 等来源解析成统一的正文和元数据结构，然后做去噪、去重、断行修复、表格结构化、标题和页码保留，并抽取权限、版本、时间、来源等元数据。这些是保证检索质量和安全边界的底座。高级层可以根据评测结果引入标题注入、上下文摘要、假想问答、多向量索引、层级索引等优化，用来提升短查询、长文档和复杂结构数据的召回效果，但这些增强会增加 token、存储和维护成本，不能替代基础清洗。工程上我会用解析成功率、有效文本比例、重复率、元数据完整率、Recall@K、nDCG 和引用可定位率来评估清洗效果。
