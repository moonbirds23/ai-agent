# 什么是 RAG？RAG 的主要流程是什么？

> 标签: RAG | 难度: 基础 | 来源: 面试鸭

---

## 一、一句话定义

**RAG = Retrieval-Augmented Generation（检索增强生成）**。

RAG 是将**信息检索（IR）**与**大语言模型（LLM）生成**结合的技术框架。典型链路是“先检索，再生成”：在 LLM 回答之前，先从外部知识库检索与问题相关的证据材料，再把这些材料作为上下文注入 Prompt，由模型基于证据生成答案。

需要注意：RAG 不是让模型“学会”知识，而是在推理时把外部知识临时提供给模型，因此更适合知识频繁变化、需要可追溯来源或涉及私有数据的场景。

---

## 二、RAG 解决的三类核心问题

### 2.1 知识时效性（Knowledge Cutoff）

LLM 的训练数据存在截止时间，且无法天然知道企业内部最新文档、业务数据或实时事件。

- **RAG 解法**：通过外部知识库持续更新文档，查询时检索最新内容并注入上下文。
- **适用边界**：前提是知识库本身更新及时、检索索引同步可靠；如果源数据过期，RAG 也会输出过期结论。
- **例子**：询问“最新产品定价规则”，RAG 从企业知识库检索现行规则，而不是依赖模型训练时的旧知识。

### 2.2 模型幻觉（Hallucination）

LLM 在缺少证据时可能生成看似合理但并不真实的内容。

- **RAG 解法**：要求模型基于检索到的文档回答，并在需要时标注来源。
- **适用边界**：RAG 可以降低幻觉风险，但不能完全消除幻觉；仍需控制检索质量、Prompt 约束、引用校验和兜底策略。
- **例子**：询问“公司内部某 API 如何调用”，RAG 检索真实接口文档，模型基于文档片段回答。

### 2.3 私有数据利用（Private Data Access）

通用 LLM 不包含企业内部文档、代码库、知识库、工单、CRM 等私有数据。

- **RAG 解法**：将私有数据解析、分块、向量化并建立检索索引，查询时按权限检索并注入上下文。
- **适用边界**：需要配套权限过滤、数据脱敏、审计日志和索引更新机制，否则可能出现越权检索或数据泄露。
- **例子**：客服系统基于内部 SOP、历史工单和产品文档回答用户问题。

## 三、RAG 的主要流程（标准五步）

```
┌─────────────────────────────────────────────────────────────────┐
│                      RAG 标准流程（Naive RAG）                    │
│                                                                 │
│  离线索引阶段                                                    │
│  文档摄入 → 清洗解析 → 分块 Chunking → Embedding → 向量库/索引     │
│                                                                 │
│  在线问答阶段                                                    │
│  用户问题 → 查询改写/向量化 → Top-K 检索 → 上下文组装 → LLM 生成   │
└─────────────────────────────────────────────────────────────────┘
```

### 3.1 离线阶段：索引构建

| 步骤 | 做什么 | 关键决策 |
|------|--------|---------|
| 文档摄入 | 从 PDF、网页、数据库、对象存储、API 等加载数据 | 格式解析、编码处理、权限信息保留 |
| 数据清洗 | 去除噪声、重复内容、无效页眉页脚 | 清洗粒度、去重规则、保留元数据 |
| 分块（Chunking） | 将长文档切成可检索的小块 | chunk size、overlap、按段落/标题/语义切分 |
| 向量化（Embedding） | 将文本转为向量表示 | 模型选型、输入长度、维度、成本 |
| 索引存储 | 保存向量、原文、元数据 | pgvector、Milvus、FAISS、Qdrant、Pinecone 等 |

### 3.2 在线阶段：查询检索与生成

| 步骤 | 做什么 | 关键决策 |
|------|--------|---------|
| 查询理解 | 对用户问题做改写、扩展或意图识别 | 是否需要 Query Rewrite / Self-Query |
| 查询向量化 | 使用与建库一致的 Embedding 模型转为向量 | 模型一致性、归一化方式 |
| 候选召回 | 从向量库或关键词索引中召回 Top-K 文档 | Dense、BM25、Hybrid、过滤条件 |
| 重排序 | 对候选文档做精排 | Cross-Encoder、RRF、规则打分 |
| 上下文组装 | 去重、压缩、截断并拼接 Prompt | Token 预算、引用、排序位置 |
| LLM 生成 | 基于检索证据回答 | 不知道时拒答、引用来源、输出格式 |

## 四、RAG 的三类演进形态

### 4.1 Naive RAG（朴素 RAG）

最基础的“索引 → 检索 → 生成”链路。优点是实现简单、成本低；缺点是检索质量不稳定，容易受分块、Top-K、Embedding 模型和 Prompt 组装影响。

**适用场景**：知识规模不大、问题类型简单、对准确率要求中等的原型或内部工具。

### 4.2 Advanced RAG（增强 RAG）

在检索前后增加工程化增强环节：

```
用户查询 → Query Rewrite / Self-Query → Hybrid Retrieval → Rerank → Context Compression → LLM
```

常见增强包括：

- 查询改写：补全上下文、消除指代、扩展同义词。
- 混合检索：结合 Dense Retrieval 与 BM25 / 关键词召回。
- 精排：用 Cross-Encoder 或规则对候选文档重新排序。
- 上下文压缩：去噪、裁剪、摘要和截断，减少无关 Token。
- 引用校验：让答案绑定来源，降低无证据生成。

**适用场景**：生产级问答、企业知识库、客服、代码知识库等对召回率和可信度要求较高的系统。

### 4.3 Modular RAG（模块化 RAG）

将 RAG 拆成可组合模块，根据任务动态选择检索策略、工具和生成方式。

- 路由：按意图选择不同知识库或检索器。
- 多路并行检索：向量、BM25、结构化数据库、知识图谱同时召回。
- 迭代检索：首次证据不足时，分解问题或二次检索。
- 缓存：高频查询、检索结果或最终回答缓存。
- Agentic RAG：由模型决定是否检索、检索什么、是否追加工具调用。

**适用边界**：模块化能力更强，但链路更长，可观测性、延迟、成本和错误传播也更复杂，需要评估收益是否覆盖复杂度。

## 五、RAG vs 其他 LLM 知识增强方案

| 方案 | 原理 | 优点 | 局限 | 适用场景 |
|------|------|------|------|---------|
| RAG | 检索外部文档并注入 Prompt | 知识可更新、可溯源、适合私有数据 | 强依赖检索质量和上下文组织 | 知识频繁变化、需要引用来源 |
| 微调 | 用领域数据调整模型参数 | 风格、格式、任务行为更稳定 | 更新知识成本高，不适合频繁事实变更 | 固定任务格式、领域表达风格 |
| Prompt Engineering | 在 Prompt 中直接写规则和少量知识 | 简单、即时生效 | 上下文有限，难维护大量知识 | 小规模规则、输出约束 |
| 预训练/继续预训练 | 大规模训练或继续训练模型 | 知识内化更深 | 成本高、周期长、难频繁更新 | 构建领域基座模型 |

**工程实践中的常见组合**：RAG 负责动态知识与证据来源，微调或 Prompt Engineering 负责输出风格、工具调用习惯和任务格式。是否组合使用取决于数据规模、更新频率、准确率要求和预算。

## 六、面试追问点

**Q: 你怎么判断一个场景是否适合 RAG？**

> 我会看三个维度：第一，知识是否频繁变化；第二，是否需要访问企业私有数据；第三，答案是否需要证据来源和较低幻觉风险。只要其中一个维度比较强，RAG 就值得评估。但前提是知识库质量、权限过滤和检索评测要跟上，否则 RAG 可能只是把错误材料更快地送给模型。

**Q: RAG 和搜索引擎有什么区别？**

> 搜索引擎主要返回文档列表，用户自己阅读和判断；RAG 在检索之后增加了证据组织和 LLM 生成步骤，直接给出综合答案。可以把 RAG 理解为“检索系统 + 上下文组装 + 受证据约束的生成”。但 RAG 不是替代搜索引擎，它仍依赖底层检索能力。

**Q: Naive RAG 最大的痛点是什么？**

> 最大痛点是检索和上下文质量不稳定。检索不到正确证据时，模型可能回答不完整或产生幻觉；检索到大量噪声时，模型容易被干扰。因此生产中通常会加入混合检索、Rerank、上下文压缩、引用校验和离线评测。

## 七、我们的项目实践（参考）

当前项目 `ai-agent` 更接近 Advanced RAG：

- Layer 1：显式参考图解析。
- Layer 2：RAG 增强检索，包括 Query Rewrite、混合检索、Rerank 归一化加权。
- Layer 3：风格模板兜底。
- 索引：图片元数据 + AI 画像文本 → `embedding-2` → pgvector。
- 上下文组装：按 `referenceMode` 裁剪字段，并控制注入字符数，避免过多无关上下文进入模型。
