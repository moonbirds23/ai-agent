# RAG 系统如何处理 PDF、Word、Markdown 等不同格式文档？

> 标签: RAG, 文档解析, 数据清洗, 多格式处理 | 难度: 🟡 中等 | 编号: QA24

---

## 一、核心结论

RAG 处理多格式文档的核心不是“把文件读成字符串”这么简单，而是建立一条统一的文档摄入管道：**格式识别 → 内容解析 → 结构保留 → 清洗去噪 → 元数据抽取 → 分块 → 建索引 → 质量评估**。

不同格式的解析方式不同，但最终应统一成标准结构：

```text
Document {
  doc_id,
  content,
  metadata: {title, source, page, section, file_type, permissions, updated_at},
  chunks[]
}
```

这样后续向量检索、BM25 检索、权限过滤、引用溯源和增量更新才能稳定工作。

---

## 二、主流处理流程

```text
PDF / Word / Markdown / HTML / Excel / 图片
  ↓
格式识别与解析器选择
  ↓
抽取正文、标题、表格、图片说明、页码、章节
  ↓
清洗页眉页脚、乱码、重复内容、无效片段
  ↓
统一为标准 Document + metadata
  ↓
按结构和 token 预算分块
  ↓
Embedding / BM25 / metadata 索引
  ↓
检索、引用、前端溯源
```

关键点是尽量保留结构信息，而不是把所有格式粗暴压成一段纯文本。

## 三、不同格式如何处理

### 3.1 PDF

PDF 分为文本型 PDF 和扫描型 PDF，两者处理方式不同。

| 类型 | 处理方式 | 注意点 |
|------|----------|--------|
| 文本型 PDF | PyMuPDF、pdfplumber、Apache PDFBox、Unstructured | 保留页码、标题、段落、表格位置 |
| 扫描型 PDF | OCR，如 Tesseract、PaddleOCR、云 OCR、多模态模型 | 记录 OCR 置信度，低质量页需人工复核 |

PDF 常见难点：

- 页眉页脚、页码、水印重复；
- 多栏排版导致阅读顺序错乱；
- 表格被解析成错位文本；
- 图注、脚注和正文关系丢失；
- 扫描件 OCR 错字影响检索。

工程建议：保留 `page_number`、`bbox`、`section`、`source_file`，便于后续引用跳转到具体页码。

### 3.2 Word / Office 文档

Word 文档可以使用 Apache POI、LibreOffice 转换、python-docx 或 Unstructured 解析。

重点保留：

- 标题层级；
- 段落；
- 表格；
- 批注和修订记录（是否保留取决于业务）；
- 页眉页脚；
- 文档属性，例如作者、更新时间、部门。

对于企业制度、合同、方案文档，Word 中的标题层级和表格往往比普通正文更重要。

### 3.3 Markdown

Markdown 是 RAG 中相对友好的格式，因为它天然包含结构。

应保留：

- `# / ## / ###` 标题层级；
- 列表和编号；
- 代码块语言；
- 表格；
- 链接；
- frontmatter 元数据。

示例：

```text
title_path = “Spring AI > VectorStore > PgVectorStore”
content = “PgVectorStore 支持相似度检索和 metadata filter...”
```

技术文档、README、API 文档通常适合按标题层级优先切分。

### 3.4 HTML / 网页

HTML 解析应区分正文和页面噪声。

常见处理：

- 用 Readability / BeautifulSoup / Jsoup 提取正文；
- 删除导航栏、广告、脚本、样式、版权声明；
- 保留标题、URL、发布时间、面包屑路径；
- 对链接做规范化，保留原始来源。

网页抓取还要注意 robots、版权、更新频率和重复页面。

### 3.5 Excel / 表格

表格不能简单按行拼接，否则容易丢失列名和单元格关系。

更合理的做法：

```text
表名: 模型配置
列: 模型名称, 维度, 最大输入
行: embedding-2, 1024, 512 tokens

转换文本:
模型 embedding-2 的维度是 1024，最大输入长度是 512 tokens。
```

对于数值查询强的场景，可以考虑结构化数据库查询，而不是全部依赖向量检索。

## 四、统一元数据设计

无论来源格式是什么，都应统一元数据字段。

| metadata 字段 | 作用 |
|---------------|------|
| `doc_id` / `chunk_id` | 去重、更新、引用映射 |
| `file_type` | PDF、Word、Markdown、HTML 等 |
| `title` / `title_path` | 检索语义增强和前端展示 |
| `page` / `section` | 引用定位 |
| `source_url` / `file_path` | 溯源 |
| `updated_at` / `version` | 增量更新和版本控制 |
| `permission_scope` | 权限过滤 |
| `parser_version` | 解析质量追踪和回滚 |
| `quality_score` | OCR 置信度、解析完整度等 |

metadata 是多格式文档 RAG 的基础能力，决定后续能否过滤、更新、引用和排查问题。

## 五、分块策略

不同格式应采用不同分块策略：

| 文档类型 | 推荐分块方式 |
|----------|--------------|
| PDF | 页码 + 标题 / 段落优先，必要时按 token 兜底 |
| Word | 标题层级 + 段落 / 表格优先 |
| Markdown | 标题层级优先，代码块和表格保持完整 |
| HTML | 正文 DOM 结构 + 标题路径 |
| Excel | 表头 + 行组，或按业务实体切分 |
| 扫描件 | OCR 后按版面、段落和页码切分 |

切分时要避免破坏表格、代码块、条款和标题上下文。对技术文档尤其建议把标题路径注入 chunk，提升短片段的可检索性。

## 六、工程落地要点

1. **解析器要可替换**：不同格式、不同质量文档需要不同 parser，避免把解析逻辑写死。
2. **保留原文和解析结果**：便于重新解析、回滚和对比解析质量。
3. **记录解析版本**：parser 升级后可识别哪些文档需要重新处理。
4. **区分文本型和扫描型 PDF**：扫描件必须走 OCR 或多模态理解。
5. **表格和代码块单独处理**：它们不是普通自然语言段落。
6. **权限字段从入库开始保留**：不能只在前端控制可见性。
7. **建立质量监控**：解析成功率、有效文本比例、OCR 置信度、元数据完整率、引用可定位率。

## 七、常见误区

| 误区 | 更准确的说法 |
|------|--------------|
| 多格式处理就是转纯文本 | 转纯文本只是第一步，还要保留结构、页码、标题、权限和来源 |
| PDF 都可以直接提取文本 | 扫描型 PDF 需要 OCR，多栏和表格 PDF 还要处理阅读顺序 |
| Markdown 不需要处理 | Markdown 需要保留标题层级、代码块、表格和链接关系 |
| 表格直接按行拼接即可 | 需要保留表头和字段关系，数值类问题可能更适合结构化查询 |
| 解析成功就代表质量好 | 还要看有效文本比例、结构完整性、引用可定位性和检索效果 |

## 八、面试回答模板

> RAG 处理 PDF、Word、Markdown 等多格式文档时，核心是把不同格式统一成标准的 Document 和 metadata，而不是简单转成纯文本。主流流程是先识别文件类型，选择合适解析器，比如 PDF 用 PyMuPDF、pdfplumber、PDFBox 或 Unstructured，扫描件走 OCR；Word 可以用 Apache POI、LibreOffice 或 Unstructured；Markdown 则保留标题层级、代码块和表格。解析后要清理页眉页脚、乱码、广告和重复内容，同时抽取 doc_id、chunk_id、标题、页码、章节、来源 URL、更新时间和权限等 metadata。分块时应优先按标题、段落、表格、代码块等结构边界切分，再用 token 上限兜底。最后再写入向量索引、BM25 索引和元数据过滤系统。工程上要重点关注解析质量、OCR 置信度、表格结构、权限过滤、引用定位和增量更新。
