# RAG 和模型微调 Fine-tuning 有什么区别？如何选择？

> 标签: RAG, 微调 | 难度: 🟡 中等 | 编号: QA8

---

## 一、核心结论

RAG 和微调解决的是两个不同层面的问题：

- **RAG**：在模型权重不变的前提下，通过检索外部知识并注入上下文，提升事实准确性、时效性和可追溯性。
- **微调**：通过训练数据更新模型权重，使模型更稳定地遵循特定任务、格式、风格或领域表达习惯。

简单说，RAG 更适合“补知识”，微调更适合“改行为”。在企业级应用中，两者经常组合使用，而不是二选一。

---

## 二、核心区别

| 维度 | RAG | 微调（Fine-tuning） |
|------|-----|-------------------|
| 技术本质 | 外部知识注入，模型参数冻结 | 参数更新，模型行为内化 |
| 知识位置 | 文档库、向量库、数据库等外部存储 | 模型权重内部 |
| 知识更新 | 更新索引即可，适合高频变化 | 需要重新训练或增量训练 |
| 可追溯性 | 可以返回来源、引用和证据片段 | 通常难以解释具体依据 |
| 幻觉控制 | 在检索质量可靠时更容易约束事实 | 仍可能生成训练外或记忆错误内容 |
| 输出格式控制 | 依赖 Prompt、工具调用或结构化输出约束 | 可通过样本稳定学习格式和风格 |
| 成本结构 | 每次请求有检索和更长上下文成本 | 训练成本较高，推理链路可更短 |
| 数据要求 | 需要可检索的高质量知识库 | 需要高质量标注样本或偏好数据 |
| 工程复杂度 | 检索、分块、索引、Rerank、引用校验 | 数据构造、训练、评估、部署和模型版本管理 |

需要注意：微调并不适合把大量经常变化的事实“背进模型”。模型可能记住部分训练信息，但这种记忆不可控、难更新，也难以提供来源。

---

## 三、分别适合什么场景

### 3.1 RAG 更适合的场景

| 场景 | 原因 |
|------|------|
| 企业文档、政策、合同、产品手册等知识频繁更新 | 更新文档和索引即可生效，不需要重训 |
| 法律、医疗、金融等需要证据支撑的问答 | 可返回来源片段，便于审计和人工复核 |
| 私有知识库问答 | 数据可留在企业内部，仅检索相关片段进入上下文 |
| 长尾知识覆盖 | 文档库天然适合覆盖大量低频知识点 |
| 需要权限过滤或多租户隔离 | 可在检索阶段按用户、部门、时间、版本做过滤 |

### 3.2 微调更适合的场景

| 场景 | 原因 |
|------|------|
| 固定格式输出 | 例如 JSON schema、工单分类、固定字段抽取，微调可提升格式稳定性 |
| 特定语气和风格 | 例如客服话术、品牌文案、代码风格、报告模板 |
| 领域任务模式稳定 | 例如文本分类、意图识别、实体抽取、固定流程决策 |
| 少量领域术语和表达习惯适配 | 可让模型更熟悉行业表达，但不应替代事实知识库 |
| 高频低延迟任务 | 在任务稳定且训练投入可接受时，微调模型可减少复杂 Prompt 或检索依赖 |

## 四、主流工程实践：不是互斥，而是组合

在真实项目中，常见组合方式是：

```
RAG 负责事实依据：检索最新、可追溯的外部知识
微调负责行为模式：稳定输出格式、语气、步骤和领域任务习惯
Prompt / Tool Calling 负责运行时约束：注入业务规则、调用工具、控制结构化输出
```

例如企业知识库助手：

1. RAG 检索最新制度文档、FAQ 和操作手册；
2. 微调或指令优化让模型稳定按“结论、依据、操作步骤、风险提示”格式回答；
3. 生成后做引用校验和权限检查，避免越权或无依据回答。

这种组合比“只微调”或“只 RAG”更稳健，但成本和工程复杂度也更高。

## 五、如何选择

### 5.1 决策流程

```
问题是否依赖外部事实知识？
  ├─ 否 → 优先 Prompt / Tool / 微调，看任务是否稳定
  └─ 是 ↓

知识是否经常变化、是否需要引用来源？
  ├─ 是 → 优先 RAG
  └─ 否 ↓

是否主要问题是输出格式、风格或任务行为不稳定？
  ├─ 是 → 考虑微调，必要时与 RAG 组合
  └─ 否 → 优先 RAG + Prompt 工程

是否已有高质量训练样本和评测集？
  ├─ 是 → 可以评估微调收益
  └─ 否 → 先做 RAG 和可观测评测，避免盲目微调
```

### 5.2 选型建议

| 需求 | 推荐方案 |
|------|----------|
| 最新知识问答 | RAG |
| 私有文档问答 | RAG + 权限过滤 + 引用校验 |
| 固定格式抽取 | Prompt / Tool Calling，必要时微调 |
| 风格一致的客服回复 | 微调或少样本 Prompt，复杂知识部分叠加 RAG |
| 法律/医疗等高风险问答 | RAG + 引用 + 审核，不建议仅依赖微调 |
| 大规模高频分类任务 | 微调或小模型蒸馏，RAG 通常不是首选 |

## 六、常见误区

| 误区 | 更准确的说法 |
|------|--------------|
| 微调可以替代 RAG | 微调适合稳定行为，不适合高频更新、需溯源的大量事实知识 |
| RAG 一定比微调更准确 | RAG 依赖文档质量、分块、检索和上下文注入；检索错误同样会导致错误回答 |
| 有了 RAG 就不需要微调 | 如果输出格式、任务流程、风格长期不稳定，微调仍有价值 |
| 微调一定成本更低 | 训练、数据构造、评估、部署和版本维护成本不可忽略 |
| 把企业知识拿去微调最简单 | 对隐私、安全、更新和可解释性要求高的企业场景，通常先做 RAG 更稳妥 |

---

## 七、面试回答模板

RAG 和微调的核心区别在于知识和能力的承载位置不同。RAG 不更新模型权重，而是把外部知识库中的相关内容检索出来注入上下文，所以更适合知识经常变化、需要来源追溯、需要权限控制的企业知识问答。微调会更新模型参数，更适合让模型稳定学习某种输出格式、语气、流程或领域任务习惯，但不适合把大量频繁变化的事实知识硬塞进模型。工程上我通常会先判断问题是“缺知识”还是“行为不稳定”：缺知识优先 RAG，行为不稳定考虑微调；复杂业务中两者可以组合，RAG 提供事实依据，微调或指令优化保证输出形式和业务流程稳定。
