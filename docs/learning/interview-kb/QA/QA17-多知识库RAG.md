# 多知识库 RAG：如何保证查询效率和准确性，并减少幻觉？

> 标签: RAG, 多知识库, 架构 | 难度: 🔴 困难 | 编号: QA17

---

## 一、问题分解

多知识库 RAG 的核心矛盾是：查询意图可能落在不同业务域，甚至同时跨多个知识库。如果全库检索，延迟、成本和噪声都会上升；如果只检索单一知识库，又可能漏掉关键证据。

因此，多知识库 RAG 需要同时解决三类问题：

| 目标 | 核心问题 |
|------|----------|
| 查询效率 | 如何避免每次请求扫描所有知识库 |
| 检索准确性 | 如何在跨库场景下召回真正相关的证据 |
| 幻觉控制 | 如何避免模型在证据不足或证据冲突时生成无依据结论 |

工程上通常采用“路由筛选 + 多路检索 + 结果融合 + 精排压缩 + 证据约束生成”的分层架构。

---

## 二、查询效率：如何避免全库扫描

### 2.1 主流方案：知识库路由

在向量检索前增加 Router，将查询分发到最可能相关的知识库。

```text
用户查询 → Router（意图识别 / 领域分类 / 元数据条件提取）
    ├─→ 技术文档库
    ├─→ 政策法规库
    ├─→ 产品知识库
    └─→ 通用知识库
```

常见路由策略：

| 方法 | 做法 | 优点 | 局限 |
|------|------|------|------|
| 规则/关键词路由 | 根据关键词、业务字段、URL 路径等规则选择知识库 | 延迟低、可解释、易兜底 | 覆盖面有限，维护成本随业务增长上升 |
| Embedding 路由 | 查询向量与知识库描述向量做相似度匹配 | 成本低，适合语义泛化 | 对库描述质量敏感 |
| LLM 分类路由 | 让模型输出目标知识库、置信度和理由 | 表达能力强，适合复杂意图 | 有额外延迟和成本，需要兜底与校验 |
| 元数据路由 | 从查询中提取时间、部门、产品线、权限等条件 | 适合企业知识库和多租户系统 | 依赖结构化元数据质量 |

主流默认做法通常是“规则/元数据优先 + Embedding 或 LLM 路由补充”，避免把所有路由决策都交给大模型。

### 2.2 并行检索 + 结果融合

当查询可能涉及多个知识库时，可以并行检索多个候选库，再统一融合：

```text
查询 → Query Rewrite / Embedding
    ├─→ 知识库 A: Top-K_a（并行）
    ├─→ 知识库 B: Top-K_b（并行）
    └─→ 知识库 C: Top-K_c（并行）
            ↓
      合并去重 → 分数归一化 / RRF 融合 → Rerank → 最终 Top-K
```

多库融合不建议直接比较不同库的原始相似度分数，因为不同库的数据分布、索引参数和距离度量可能不同。常见做法是使用 RRF（Reciprocal Rank Fusion，倒数排名融合）或归一化后的加权融合。

```text
RRF_score(d) = Σ 1 / (k + rank_i(d))
```

RRF 的优点是更依赖排序名次，而不是依赖各检索器的原始分数绝对值，因此适合混合检索和多库检索场景。

### 2.3 知识库摘要预筛选

每个知识库维护一段结构化描述，例如覆盖范围、更新时间、数据来源、权限范围和典型问题。查询先与这些库级摘要做匹配，再选择 Top-N 个知识库进入正式检索。

```text
知识库摘要匹配 → 选择候选库 1~N 个 → 库内向量/关键词检索
```

该方案适合知识库数量较多的系统，可以减少无关库检索带来的延迟和噪声。但库级摘要需要维护，知识库内容变化后也要同步更新摘要。

## 三、准确性：跨库检索质量保障

### 3.1 统一或对齐 Embedding 空间

如果多个知识库需要在同一检索器中比较分数，通常应使用同一个 Embedding 模型、维度、归一化方式和距离度量。不同模型生成的向量空间不直接对齐，跨库混排可能失真。

如果业务上必须使用不同模型，例如代码库和文本库分别使用专用 Embedding，则更适合采用“库内检索 + 排名融合 + Rerank”，而不是直接比较原始向量距离。

### 3.2 Query Rewrite 前置

多知识库场景中，用户问题经常包含省略、指代和业务上下文。检索前可以先做 Query Rewrite：

```text
原始问题: “这个策略对旗舰版也生效吗？”
改写后: “产品定价策略中的某项规则是否适用于旗舰版套餐？”
```

增强版本可以让 Rewrite 输出结构化结果：

```json
{
  "rewritten_query": "产品定价策略是否适用于旗舰版套餐",
  "candidate_kbs": ["产品知识库", "定价规则库"],
  "filters": {"product_tier": "旗舰版"}
}
```

### 3.3 来源和元数据标记

每个检索结果必须携带来源库标识、文档 ID、chunk ID、标题、页码或 URL 等元数据。

```text
Chunk 内容: "Spring AI 的 ChatClient 提供 Advisor 链机制..."
元数据: {
  source_kb: "技术文档库",
  doc_id: "spring-ai-guide-v1",
  chunk_id: "spring-ai-guide-v1#p42-c3",
  page: 42,
  updated_at: "2025-05-20"
}
```

来源标识有三类作用：

1. Rerank 时可以控制同源结果占比，避免单一知识库垄断上下文；
2. 生成时可以提供引用编号和溯源信息；
3. 排障时可以追踪错误答案来自哪个知识库或哪类文档。

### 3.4 跨库去重和冲突处理

不同知识库可能包含重复、近重复或互相冲突的信息。常见处理方式包括：

- 对完全重复内容用 hash 去重；
- 对近重复 chunk 用 SimHash、MinHash 或语义相似度去重；
- 对同一事实的多个来源，按来源可信度、更新时间、业务优先级排序；
- 如果证据冲突且无法自动裁决，答案中应显式说明存在冲突，而不是合成一个确定结论。

## 四、减少幻觉：从检索到生成的防护链

### 4.1 检索层：相关性阈值与空检索保护

多知识库检索会扩大候选池，也会增加噪声。需要设置相关性阈值、最小证据数量和空检索保护。

```text
if no_relevant_context:
    返回“基于当前知识库无法回答”或触发澄清问题
```

阈值不宜直接照搬其他项目，因为不同 Embedding 模型和向量库的分数分布不同。更稳妥的做法是通过验证集和线上反馈确定阈值。

### 4.2 上下文层：边界隔离与噪声控制

检索内容应使用明确结构注入，避免模型混淆系统指令、用户问题和检索资料。

```xml
<retrieved_context id="1" source_kb="技术文档库" score="0.89">
Spring AI 提供 ChatClient 和 Advisor 链机制...
</retrieved_context>
```

同时要进行上下文压缩和去重，避免把大量低相关内容注入 Prompt 形成上下文噪声注入。过多噪声可能导致模型忽略关键证据，或把不同来源的信息错误拼接。

### 4.3 生成层：证据约束与拒答策略

Prompt 中应明确约束模型只基于检索上下文回答：

```text
请仅基于 <retrieved_context> 中的证据回答。
如果证据不足，请回答：“基于当前知识库，我无法确定答案。”
不要补充未被证据支持的事实。
```

这里的重点不是简单要求模型“不要编造”，而是建立证据边界：无证据时拒答，证据不足时降置信度，证据冲突时说明冲突。

### 4.4 生成后验证与引用校验

高可信场景可以对生成结果做二次验证：

```text
答案 → 抽取事实断言 → 关联引用 chunk → 判断是否有证据支撑 → 删除/改写/降置信度
```

同时检查引用编号是否来自系统提供的候选来源，防止模型生成不存在的引用。

## 五、主流默认方案与高可信增强方案

### 5.1 主流默认方案

适合大多数企业知识库和业务问答：

```text
规则/Embedding 路由 → 候选库并行检索 → RRF/归一化融合 → Rerank → 上下文压缩 → 带引用生成
```

特点是复杂度适中、容易落地，能兼顾效率和检索质量。

### 5.2 高可信增强方案

适合法务、医疗、金融、合规、生产运维等风险较高场景：

- LLM 路由输出置信度，低置信度时多库并行或向用户澄清；
- 多检索器融合：向量检索 + BM25 + 元数据检索 + 图谱关系检索；
- Cross-Encoder 或 LLM-as-Reranker 精排；
- 断言级引用校验和反向检索验证；
- 冲突证据检测与显式冲突回答；
- 全链路 trace：记录路由、召回、融合、精排、压缩和引用映射。

这些方案能提高可信度，但会带来额外延迟、成本和系统复杂度，不应作为所有场景的默认起点。

## 六、总结

| 目标 | 核心手段 |
|------|----------|
| 查询效率 | 路由分发、库级摘要预筛选、候选库并行检索、超时降级 |
| 检索准确性 | 统一/对齐 Embedding 空间、Query Rewrite、元数据过滤、RRF 融合、Rerank、跨库去重 |
| 幻觉控制 | 相关性阈值、空检索保护、上下文边界隔离、拒答策略、引用校验、生成后验证 |

三者是分层递进关系：路由和并行检索降低无效查询成本；融合、去重和精排提高证据质量；上下文边界、拒答策略和引用校验降低无证据生成风险。

## 七、面试回答模板

> 多知识库 RAG 的难点在于既不能每次全库扫描，也不能过早路由导致漏召回。我一般会分层设计：第一层做知识库路由，优先用规则、元数据和库级摘要筛选候选库，复杂意图再用 LLM 分类；第二层对候选库做并行检索，并用 RRF 或归一化分数做结果融合，避免不同库分数不可比；第三层用 Rerank、去重和上下文压缩得到高质量证据；第四层在生成阶段要求模型只基于检索证据回答，证据不足时拒答，并输出系统控制的引用编号。高可信场景还会增加断言验证、引用支撑校验和冲突证据检测。这样可以在效率、准确性和幻觉控制之间取得工程上可落地的平衡。
