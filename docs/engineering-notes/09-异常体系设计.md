# 09 — 异常体系设计

## 设计理念

> 统一异常类 + 错误码枚举 + 全局处理器 = 简洁、一致、可维护

不搞多层异常继承（`AiApiException`、`ContentSafetyException`...），一个 `BusinessException` 覆盖所有业务异常。

## 三层结构

```
ErrorCode (枚举)
  ↓ 被使用
BusinessException (RuntimeException)
  ↓ 被捕获
GlobalExceptionHandler (@RestControllerAdvice)
  ↓ 输出
BaseResponse { code, data:null, message }
```

## ErrorCode — int 码枚举

```java
public enum ErrorCode {
    SUCCESS(0, "ok"),

    // 40xxx — 客户端错误
    PARAMS_ERROR(40000, "请求参数错误"),
    EMPTY_MESSAGE(40100, "消息不能为空"),
    MESSAGE_TOO_LONG(40101, "消息过长"),
    IMAGE_TOO_LARGE(40001, "图片过大"),
    CONTENT_BLOCKED(40200, "内容违规"),

    // 50xxx — AI 服务错误
    AI_AUTH_FAILED(50000, "AI 认证失败"),
    AI_RATE_LIMIT(50001, "AI 频率限制"),
    AI_TIMEOUT(50002, "AI 调用超时"),
    AI_MODEL_UNAVAILABLE(50003, "AI 模型不可用"),
    IMAGE_GENERATION_FAILED(50005, "图片生成失败"),
    IMAGE_ANALYSIS_FAILED(50006, "图片分析失败"),

    // 50010 — 记忆/存储错误
    MEMORY_ERROR(50010, "记忆操作失败"),
    GALLERY_OPERATION_FAILED(50011, "图库操作失败"),
    PROFILE_OPERATION_FAILED(50012, "画像操作失败"),

    // 59999 — 系统兜底
    SYSTEM_ERROR(59999, "系统错误");
}
```

**码段分配原则**：
- `0`：成功
- `40xxx`：客户端的问题（参数错、格式错、权限不够）
- `50xxx`：服务端的问题（AI 挂了、DB 挂了、代码 Bug）
- 各段内部留有空隙，方便插新错误码

## BusinessException

```java
public class BusinessException extends RuntimeException {
    @Getter
    private final int code;

    // 三个构造函数
    public BusinessException(ErrorCode errorCode)                    // code + 默认消息
    public BusinessException(ErrorCode errorCode, String detail)     // code + 自定义消息
    public BusinessException(int code, String message)               // 手动指定 code
}
```

**为什么不继承受检异常？** Spring 的事务管理、lambda 表达式、Stream API 都对受检异常不友好。`RuntimeException` 是最务实的选择。

## GlobalExceptionHandler

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // ① 业务异常 → 直接透传 code + message
    @ExceptionHandler(BusinessException.class)
    public BaseResponse<?> handleBusiness(BusinessException e) {
        log.warn("BusinessException: code={}, message={}", e.getCode(), e.getMessage());
        return ResultUtils.error(e.getCode(), e.getMessage());
    }

    // ② 参数校验失败 → 聚合字段错误
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public BaseResponse<?> handleValidation(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
            .map(f -> f.getField() + ": " + f.getDefaultMessage())
            .collect(Collectors.joining("; "));
        return ResultUtils.error(ErrorCode.PARAMS_ERROR.getCode(), msg);
    }

    // ③ 未知异常 → 记录完整堆栈，返回到泛化消息
    @ExceptionHandler(Exception.class)
    public BaseResponse<?> handleException(Exception e) {
        log.error("Unexpected error", e);
        return ResultUtils.error(ErrorCode.SYSTEM_ERROR);
    }
}
```

**关键设计**：
- 返回 `BaseResponse<?>`，不设置 `@ResponseStatus`（HTTP 状态码始终 200）
- 未知异常不暴露内部细节给客户端（安全考虑）
- 业务异常的 message 直接透传（用户友好的中文提示）

## ThrowUtils — 统一异常抛出入口

```java
public class ThrowUtils {
    public static void throwIf(boolean condition, ErrorCode errorCode) {
        if (condition) throw new BusinessException(errorCode);
    }

    public static void throwIf(boolean condition, ErrorCode errorCode, String detail) {
        if (condition) throw new BusinessException(errorCode, detail);
    }
}
```

**使用规范**：业务校验一律用 `ThrowUtils.throwIf()`，不直接 `new BusinessException(...)`。
```java
// ✅ 推荐
ThrowUtils.throwIf(message.length() > 2000, ErrorCode.MESSAGE_TOO_LONG);

// ❌ 不推荐
if (message.length() > 2000) throw new BusinessException(ErrorCode.MESSAGE_TOO_LONG);
```

## 异常处理全景图

```
Controller 层：    不 try-catch，异常向上抛
                      │
                      ▼
Advisor 层：       ExceptionGuard(MAX) 做第一层兜底
                   • BusinessException → 友好回复
                   • 其他异常 → 泛化消息
                      │
                      ▼
Controller 层：     未捕获的异常
                      │
                      ▼
GlobalExceptionHandler：做最终兜底
                   → BaseResponse { code:xxx, data:null, message:"..." }
                   → HTTP 200
```

## 已知不足

1. **缺少 `ConstraintViolationException` 处理**：`@Validated` 在类级别的校验抛的是 `ConstraintViolationException`，不是 `MethodArgumentNotValidException`，当前会落入泛型 59999
2. **缺少 `HttpMessageNotReadableException` 处理**：请求体 JSON 格式错误时应返回友好提示，当前返回 59999
3. **无国际化**：所有消息硬编码中文，未使用 Spring 的 `MessageSource`
