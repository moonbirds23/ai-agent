# Phase 1：修正确性问题（本周，13 项）

## 1.1 修复 ExceptionGuardAdvisor 顺序 —— 双层兜底

**来源**：Bug 审查 C1 ｜ **优先级**：🔴 致命

**问题**：`ExceptionGuardAdvisor.getOrder()` 返回 `Integer.MAX_VALUE`，在链中最后执行。`try/catch` 只包住了 `chain.nextCall()`，前面 Advisor 的异常全部穿透。

**修复**：`advisor/ExceptionGuardAdvisor.java` L64-66

```java
// 改前
public int getOrder() { return Integer.MAX_VALUE; }

// 改后
public int getOrder() { return Integer.MIN_VALUE; }
```

**双层兜底策略**（D1 确认）：
- 外层（ExceptionGuard）：捕获 Advisor 链内所有 `BusinessException`，转友好文案
- 内层（ChatServiceImpl `.onErrorResume`）：保留不动，作为流式响应包装层的额外防线
- 两者不冲突——ExceptionGuard 先捕获则内层不触发；ExceptionGuard 未覆盖的路径（如 Flux 组装阶段的异常）由内层兜底

**验证**：单元测试让 `ContentGuard.validate()` 抛 `BusinessException`，断言 `ExceptionGuard.friendlyResponse()` 被触发。

## 1.3 修复 RagInjectionAdvisor / PromptOptimizeAdvisor 替换所有 UserMessage

**来源**：Bug 审查 H1-H2 ｜ **优先级**：🔴 致命

**问题**：两个 Advisor 的循环替换了 Prompt 中**每一个** `UserMessage`（包括 MCMA 注入的历史消息），导致 LLM 看到的历史对话被当前文本覆盖。

**修复**：`advisor/RagInjectionAdvisor.java` L54-59 + `advisor/PromptOptimizeAdvisor.java` L58-63

## 1.4 修复 Rerank 评分归一化

**来源**：Bug 审查 H3 ｜ **优先级**：🔴 高风险 ｜ **决策 D2**

**问题**：`vectorScore`(0~1)、`keywordScore`(0~50+)、`metadataScore`(0~50+) 量纲不同，标签匹配碾压语义相似度。

**修复**：`service/impl/RagRerankerImpl.java` ——批次内 min-max 归一化

```java
double maxVector = candidates.stream()
    .mapToDouble(RagCandidate::vectorScore).max().orElse(1.0);
double maxKeyword = candidates.stream()
    .mapToDouble(RagCandidate::keywordScore).max().orElse(1.0);
double maxMetadata = candidates.stream()
    .mapToDouble(RagCandidate::metadataScore).max().orElse(1.0);

double finalScore =
    (c.vectorScore() / maxVector) * ragProperties.vectorWeight()
    + (c.keywordScore() / Math.max(maxKeyword, 1.0)) * ragProperties.keywordWeight()
    + (c.metadataScore() / Math.max(maxMetadata, 1.0)) * ragProperties.metadataWeight();
// 每个分值独立归到 0~1，保持量纲一致
```

## 1.13 画像分析改为同步

**来源**：Bug 审查 M2 ｜ **优先级**：🟡 中风险 ｜ **决策 D4**

**当前**：`@Async` 事件触发 `PictureAutoAnalysisListener`，导致同一张图可能被调两次视觉模型。

**改为**：入库后同步执行分析，结果缓存供当前请求复用。

```java
// GalleryServiceImpl.upload() / importUrl() — 改 sync
private GalleryPicture uploadInternal(...) {
    // ... save + storage ...
    // 同步分析（替代 publishEvent + @Async）
    try {
        profileService.analyzeDirect(withUrl, decoded.bytes(), contentType);
    } catch (Exception e) {
        log.warn("[GalleryService] 自动画像分析失败，已入库但未生成画像 pictureId={}", saved.id(), e);
        // 不阻塞返回，标记 vector_status = -2（待重试）
    }
    return withUrl;
}
```

**`PictureAutoAnalysisListener`** 改为重试补偿器：定时扫描 `vector_status = -2` 的记录，重新触发分析。

**收益**：
- 消除重复视觉模型调用
- 入库后画像立即可用于后续检索
- 异步失败有补偿机制

# Phase 5：Picture-Backend 对接规划（仅定义，不实施）

> **决策 D5**：当前阶段不启动代码对接。Phase 1~2 完成后再评估最佳时机。以下为接口契约草案，供后续联调参考。

## 5.1 对接定位

```
Picture-Backend（主业务系统）
  负责：登录、用户、空间权限、图片主表、COS、审核、额度、协作

ai-agent-master（AI/RAG 子服务）
  负责：图片画像、向量索引、RAG 检索、提示词增强、AI 生图/分析、RAG Trace
```

**核心原则**：前端只请求 Picture-Backend；AI 子服务只接收主系统已校验的可信上下文。

## 5.2 两项目技术栈差异

| 差异项 | Picture-Backend | ai-agent-master |
|-------|-----------------|-----------------|
| Java | 8 | 21 |
| Spring Boot | 2.6 | 3.5 |
| 数据库 | MySQL | PostgreSQL + pgvector |
| 鉴权 | Sa-Token | 缺失 |
| 图片主表 | `picture` | `gallery_picture` |

**结论**：短期采用主系统代理 + AI 子服务方式。长期如果要合并，需先升级 Picture-Backend 到 Java 21 + Spring Boot 3。

## 5.3 推荐架构

```
前端 → Picture-Backend → AI 子服务（内网）
                ↓
        Sa-Token 鉴权 + 空间权限校验（在调用 AI 之前完成）
```

AI 子服务只暴露内网接口，请求体必须携带：`requestId`、`userId`、`spaceId`、`permissionList`。

## 5.4 接口契约草案

### Picture-Backend 对前端暴露

| 接口 | 说明 |
|------|------|
| `POST /api/ai/chat` | AI 对话 |
| `POST /api/ai/generate` | AI 生图 |
| `POST /api/ai/picture/{id}/analyze` | 图片 AI 分析 |
| `GET /api/ai/rag/trace/{traceId}` | RAG 追踪（管理端） |

### ai-agent-master 对内暴露

| 接口 | 说明 |
|------|------|
| `POST /internal/ai/pictures/index` | 创建/更新画像与向量索引 |
| `DELETE /internal/ai/pictures/{id}/index` | 删除画像与向量索引 |
| `POST /internal/ai/rag/chat` | RAG 对话 |
| `POST /internal/ai/rag/generate` | RAG 生图 |
| `POST /internal/ai/images/analyze` | 视觉分析 |

## 5.5 图片生命周期同步

```
Picture-Backend 上传成功 → 事务后触发 AiIndexSync → AI 子服务分析+建索引
Picture-Backend 编辑标签   → 事务后触发 reindex   → AI 子服务更新画像+向量
Picture-Backend 删除/拒审  → 触发 removeIndex     → AI 子服务清画像+向量
```

## 5.6 字段映射

| Picture-Backend `picture` | AI 侧使用 | 说明 |
|--------------------------|----------|------|
| `picture.id` | `externalPictureId` | 唯一索引 `(sourceSystem, externalPictureId)` |
| `picture.userId` | 权限过滤 | RAG 检索按 userId 隔离 |
| `picture.spaceId` | 权限过滤 | 公共/私有/团队空间边界 |
| `picture.reviewStatus` | 是否可索引 | 仅审核通过图片进入 RAG |
| `picture.isDelete` | 删除索引依据 | 必须同步删除向量 |

## 5.7 上线策略

```
第 1 阶段：仅管理员可用
第 2 阶段：开放测试用户和指定空间
第 3 阶段：开放普通用户 + 每日额度限制
第 4 阶段：根据成本/稳定性放开
```

降级策略：AI 不可用时不影响图片基础功能（上传/编辑/删除）。
